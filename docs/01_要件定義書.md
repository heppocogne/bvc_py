# bvc 要件定義書

- 文書バージョン: 0.5(2026-09-25)
- ツール名 `bvc`(Binary Version Control)は仮称

---

## 1. 目的

アプリケーションが生成する大容量バイナリファイルを、**容量効率よく**、**データを失わない**形でバージョン管理する。
操作感は「undo/redo の発展形」とし、版の差し戻し、差し戻しの取り消し、変更へのコメントができることを主目的とする。

## 2. 前提と制約

| 項目 | 内容 |
|---|---|
| 利用者 | 1人。同時編集・競合は考慮しない |
| リモート | 扱わない。ローカルのみ |
| 対象ファイル数 | リポジトリあたり最大10程度(超えても動作すること) |
| ファイルサイズ | 概ね1GB以下(超えても動作すること) |
| コミット回数 | 概ね100回以下(超えても動作すること) |
| 実装言語 | Python 3.10以降、開発時を除き**標準ライブラリのみ** |
| 対象OS | Windowsを主に想定。Linux/macOSでも動作すること |
| UI | 当面はCLIのみ。将来、簡易GUIを追加できる構造にする |
| ファイルの性質 | 同じファイルの版同士でどこが変わるかは不明。末尾追記だけではない。圧縮率はzipで約0.6〜0.9倍 |

## 3. 用語

| 用語 | 意味 |
|---|---|
| 作業フォルダ | 利用者がアプリで扱うファイルがあるフォルダ。`.bvc/` を置く場所 |
| 追跡ファイル | 設定で明示したパターンに一致するファイル |
| 版(コミット) | 追跡ファイル全体のスナップショット。番号で識別する |
| 現在位置(`@`) | 作業フォルダが対応している版 |
| ブランチ | 版の枝。名前は任意 |
| 自動コミット | 現在位置を動かす操作の前に、未コミットの変更を自動で保存した版 |

## 4. 機能要件

### 4.1 基本操作

| ID | 操作 | 要件 |
|---|---|---|
| F-01 | init | リポジトリを作成し、追跡パターンを登録する。その時点の追跡ファイルを版 `0` として記録する |
| F-02 | commit | 追跡ファイルの現状を新しい版として記録する。現在位置に子がある場合は新しいブランチを作る。子が無ければ現在のブランチに追加する |
| F-03 | log | 版のツリー、メッセージ、コメント、現在位置、未コミットの変更の有無を表示する |
| F-04 | undo | 1つ前の版へ移動し、作業ファイルをその版に戻す |
| F-05 | redo | 現在のブランチの先端方向へ1つ進み、作業ファイルをその版にする |
| F-06 | goto | 任意の版、またはブランチの先端へ移動する |
| F-07 | note | 版にコメントを追記する(後からでも可)。本文と対象の版はオプションで明示し、取り違えが起きない書式にする |
| F-08 | branch | ブランチを一覧表示し、名前を付ける・外す。名前なしのブランチも許容する |
| F-09 | discard | 指定の版を削除する。現在位置の版を削除した場合は親の版に戻る。子の版は親につなぎ直す |
| F-10 | gc | 削除済みの版と、どこからも参照されないデータを実際に削除する |

### 4.2 補助操作

| ID | 操作 | 要件 |
|---|---|---|
| F-11 | verify | 保存データ全体の整合性(ハッシュ)を検証する |
| F-12 | sync | git の `bvc.lock` が指す内容に作業ファイルを合わせる |
| F-13 | git install-hooks | git フックを設置する |

### 4.3 ステージング不要(自動取り込み)

- F-20: `git add` に相当する操作は設けない。追跡パターンに一致するファイルは自動で対象になる。
- F-21: 現在位置を動かす操作(undo/redo/goto/discard/sync)の前に未コミットの変更があれば、自動コミットとして保存する。メッセージには元になった操作と引数を記録する(例: `auto: before goto 5`)。
- F-22: status コマンドは設けない。未コミットの変更は log に表示する。

### 4.4 ファイルの欠落と名前変更

- F-30: 前の版にあった追跡ファイルが無い場合、既定では処理を中止し、利用者に知らせる。
- F-31: `--allow-missing` を指定したときだけ、無いファイルを削除として記録する。
- F-32: 名前の変更は内容から自動で検知する。完全一致、またはチャンクの類似度で判定する。
- F-33: 自動検知が外れた場合に備え、`--rename 旧=新` で手動指定できる。
- F-34: 変更後の名前が追跡パターンから外れた場合は、中止時にヒントを表示する。

### 4.5 版の指定(jujutsu 風)

- F-40: `0` は init 時点、`1` はその次、というように連番で指定する。番号は再利用しない。
- F-41: `@` は現在位置、`@-` は親、`@+` は現在のブランチ方向の子を表す。接尾辞は連結できる(`@--`、`5-`)。
- F-42: ブランチ名で、そのブランチの先端を指定できる。
- F-43: ブランチには内部で番号を持たせるが、利用者には見せない。版番号との取り違えを防ぐため、指定に使う番号は版番号だけとする。名前のないブランチの先端へは、log で版番号を確認して移動する。

### 4.6 git 連携

- F-50: バイナリ本体は git に入れない。内容を指すポインタファイル `bvc.lock` を git で管理する。
- F-51: 現在位置が動くたびに `bvc.lock` を自動で更新する。
- F-52: git 側で過去の版に戻したとき、`bvc sync` でバイナリも対応する版に戻せる。フックで自動化できる。
- F-53: git のコミットが参照している版は、discard で警告し、gc では削除しない。

## 5. 非機能要件

### 5.1 安全性(最優先)

| ID | 要件 |
|---|---|
| N-01 | 利用者の明示的な削除操作(discard→gc)以外で、記録済みのデータを失わない |
| N-02 | 未コミットの作業内容を、bvc の操作で失わない(F-21) |
| N-03 | 処理中に強制終了や電源断が起きても、リポジトリは壊れない。残るのは参照されないゴミだけ |
| N-04 | 作業ファイルの復元は「全部成功か全部元通り」とする。途中で失敗した場合や、強制終了後に再起動した場合も、中途半端な状態を残さない |
| N-05 | データには SHA-256 を持たせ、復元時と verify 時に照合する |
| N-06 | 他のアプリが使用中・書き込み中のファイルを検出し、処理を中止する |
| N-07 | 二重起動を防止する(ロック) |
| N-08 | 全操作を、操作前後の状態付きで追記型ログに残す |

### 5.1.1 破損への耐性

| ID | 要件 |
|---|---|
| N-40 | 一部のチャンク・マニフェスト・版ファイルが欠損・破損していても、他の版の読み出しと、新しいコミットは続けられる |
| N-41 | 新しいコミットは、既存の壊れたデータを参照しない(壊れたチャンクを重複排除で再利用しない) |
| N-42 | 壊れた版を飛び越えて、それより前の健全な版に戻れる。壊れた版へは移動できなくてよいが、移動しようとした場合は作業ファイルを変えずに中止する |
| N-43 | 破損を検出したデータは隔離し、以後の処理で使わない |
| N-44 | 作業ファイルに同じ内容があれば、壊れたデータを修復できる |
| N-45 | 管理ファイル(HEAD, counters, index, branches)が壊れても、自動で復旧できる。名前などの付随情報は失われてもよい |
| N-46 | 復号後のサイズを記録値で制限し、改ざんされたデータで大量のメモリやディスクを消費しない |

### 5.1.2 パスの安全性

| ID | 要件 |
|---|---|
| N-47 | リポジトリ内のデータ(版・マニフェスト・設定・bvc.lock)が書き換えられていても、作業フォルダの外や `.bvc/` の中に書き込んだり、削除したりしない |
| N-48 | ハッシュ値や番号など、ファイル名に使う値は形式を検査してから使う |
| N-49 | 作業フォルダ内のシンボリックリンク・ジャンクションはたどらず、追跡もしない |
| N-50 | 作業フォルダを移動・改名しても、そのまま使える(パスは相対で保持する) |

### 5.2 性能

| ID | 要件 |
|---|---|
| N-10 | 未変更のファイルはサイズと更新日時で判定し、中身を読まない |
| N-11 | ハッシュ計算と圧縮はスレッドで並列化する |
| N-12 | メモリ使用量はファイルサイズに比例させない(ストリーム処理) |

参考として、検証環境(Python 3.11・2コア)での実測値は次の通り。SHA-256 は約1GB/s。zlib(レベル1)は1コアあたり約40MB/sで、スレッド数に比例して速くなる。純Python実装のCDCは約10MB/s。

### 5.3 容量効率

| ID | 要件 |
|---|---|
| N-20 | 版の間で共通する部分(チャンク)は1回だけ保存する |
| N-21 | 分割方式(固定長/CDC/分割しない)は差し替え・選択が可能。ファイルのパターンごとにも選べる。途中で切り替えても既存データは読める |
| N-22 | 圧縮は設定で選べる(auto/none/zlib)。縮まないデータは無圧縮で保存する |
| N-23 | 「分割しない」+「圧縮しない」の組み合わせでは、保存データが元ファイルそのもの(1バイトのヘッダ付き)になり、bvc が使えなくても手作業で取り出せる |

### 5.4 拡張性

| ID | 要件 |
|---|---|
| N-30 | repo 層は表示用の文字列ではなくデータ(dataclass)を返す。CLI で整形し、`--json` 出力にも対応する |
| N-31 | 作業フォルダのパスとリポジトリのパスをコード上で分離し、将来リポジトリを別の場所に置けるようにする |
| N-32 | 分割方式と圧縮方式はプラグイン的に追加できる |

### 5.5 保存形式の互換性(将来対応。枠組みだけ先に用意する)

| ID | 要件 |
|---|---|
| N-60 | 保存するファイルにはすべて `format` 番号を持たせる |
| N-61 | 知らない(新しい)形式を見つけた場合は、何も書き込まずに明確なエラーで中止する |
| N-62 | 新しいバージョンのツールは、古い形式を読める。形式の変換が必要な場合は、明示的なコマンドで行う |

## 6. 対象外

- マージ、リモート、複数人運用、ファイルのロック
- バイナリの差分表示
- GUI(将来対応)

## 7. 決定事項

| # | 論点 | 決定 |
|---|---|---|
| D-1 | 分割方式 | 仮に固定長とし、CDC・分割しない(whole)に差し替え・選択できる設計にする |
| D-2 | ステージング | 設けない(jujutsu 風の自動取り込み) |
| D-3 | 自動コミット | 元になった操作が分かるメッセージを付けて履歴に残す |
| D-4 | 追跡対象 | 明示したパターンのみ(例外用の除外パターンあり) |
| D-5 | discard の子 | 親につなぎ直す |
| D-6 | 復元の失敗時 | 全部成功か全部元通り |
| D-7 | ファイルの欠落 | 既定で中止。`--allow-missing` で削除扱い。名前変更は自動検知(`--rename` は予備) |
| D-8 | 版の指定 | jujutsu 風。`0` は init 時点のファイル |
| D-9 | リポジトリの場所 | 当面は作業フォルダ内の `.bvc/`。後で変更可能な構造にする |
| D-10 | Python | 3.10以降 |
| D-11 | repo 層の返り値 | データ(dataclass) |
| D-12 | git 連携 | ポインタファイル `bvc.lock` とフック。フィルタ(clean/smudge)方式は採用しない |
| D-13 | 破損時の方針 | 壊れた版は移動不可とする。飛び越えての移動と、新規コミットは可能とする。検出したら隔離し、作業ファイルから修復できるようにする |
| D-14 | コミット時の既存チャンク検査 | 既定は存在とヘッダの検査のみ。設定で完全検査(読み出してハッシュ照合)にできる |
| D-15 | 基本方針 | 判断に迷う場面では安全側(何も変えずに中止)に倒す |
| D-16 | 上書き・削除前の確認 | 復元で上書き・削除する作業ファイルは、stat キャッシュに頼らず、必ず中身をハッシュして保存済みであることを確認する。追跡対象外のファイルがある場所には書き出さない |
| D-17 | git との整合 | 存在しない、または壊れた版を指す bvc.lock は、git にコミットさせない。git 連携が有効なときは、gc で git の履歴を必ず確認する |
| D-18 | ブランチ | 先端に commit すると自動で伸びる(git 型)。名前もそれに追従する。ある時点を固定で指す印(タグ)は、必要になったら別機能として追加する |
| D-19 | 版の指定に使う番号 | 版番号のみ(0, 1, ..., @-, @, @+など)。ブランチ番号(`b<N>`)による指定は取り違え防止のため廃止するが、ブランチ名では指定できるようにする。 |
| D-20 | 終了コード | 0 は「要求された状態になった」(すでに成立していた場合を含む)。変更なしの commit は 0。要求された移動ができない場合(根での undo、先端での redo)は 4 |
| D-21 | note の書式 | `note -m <本文> [-r <版>]`。位置引数で版と本文を区別しない |
