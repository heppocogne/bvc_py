## 1. 機能(正常系)

| # | 観点 | 確認内容 |
|---|---|---|
| F-1 | ○ 各コマンドの基本動作 | init/commit/log/undo/redo/goto/note/branch/discard/gc/verify/sync が仕様通りに動く。各段階で作業ファイルのハッシュが期待値と一致する |
| F-2 | ○ ブランチ規則 | 先端での commit はブランチを延長する。途中からの commit は新しいブランチを作る。discard で子が無くなった版からの commit は、元のブランチを延長する |
| F-3 | ○ undo/redo の往復 | 分岐がある状態で undo → redo を繰り返すと、元のブランチ方向へ戻る。goto の後は、移動先のブランチ方向に redo する |
| F-4 | ○ 自動コミット | 未コミットの変更がある状態で移動すると、auto 版ができる。メッセージにコマンドと引数が入る。redo で編集内容に戻れる |
| F-5 | ○ リビジョン式 | `0`、`@`、`@-`、`@--`、`@+`、`5-`、名前。存在しない番号、根の `-`、先端の `+`、discard 済みの番号は、正しくエラーになる |
| F-6 | ○ 名前変更の検知 | 完全一致、類似(しきい値の前後)、手動指定の優先、同一内容の複数ファイル、パターン外へのリネームでのヒント表示 |
| F-7 | ○ 欠落 | 既定で中止(終了コード3)。`--allow-missing` で削除として記録される。移動系でも同様 |
| F-8 | ○ discard のつなぎ直し | 途中、分岐点、根、現在位置の版を discard する。連続して discard する。discard 後の log・undo・redo・commit が正しく動く |
| F-9 | ○ gc | 削除済みの版と不要データだけが消え、有効な版はすべて復元できる。`--dry-run` では何も変わらない。pin された版は残る |
| F-10 | ○ 分割方式・圧縮の切り替え | fixed → gear → whole → fixed、auto → none → zlib と切り替えても、全ての版が復元できる。rules によるパターン別の指定が正しく適用される |
| F-11 | ○ --json 出力 | 全コマンドの出力が JSON として解析でき、dataclass の内容と一致する |
| F-12 | ○ 終了コード | 仕様書 2.2節の分類通りになる。変更なしの commit・現在位置への goto・同期済みの sync は 0 で `changed: false`、根での undo・先端での redo は 4 で、データは変わらない |
| F-13 | ○ whole + none の手作業復旧 | 保存データの先頭1バイトを除いたものが、元ファイルとバイト単位で一致する |
| F-14 | ○ note の書式 | `note -m 2`、`note -m "2 回目"`、`note -m x -r 3` が意図通りの版に付く。本文を省いた場合はエラーになる |

## 2. パス・ファイルシステム

| # | 観点 | 確認内容 |
|---|---|---|
| P-1 | ◎ 記録されたパスの改ざん | 版・マニフェスト・bvc.lock・journal のパスを、`../x`、絶対パス、`C:\x`、`\\server\x`、`.bvc/config.json`、`CON`、空文字、制御文字、NFC でない形、Windows の 8.3 形式の短い名前(`BVC~1/x`)に書き換える。いずれの場合も、作業フォルダの外や `.bvc/` の中に書き込み・削除をせず、その版は「壊れた版」になる(8.3 形式の短い名前は、名前だけでは判定できないため、移動時に何も変えずに中止する) |
| P-2 | ○ ハッシュ・番号の改ざん | マニフェスト名やチャンク名に `../`、大文字、長さ違い、16進以外の文字を入れる。版番号を負数、巨大な数、文字列、小数にする。いずれも形式エラーとして扱い、その文字列をパスに使わない |
| P-3 | ○ シンボリックリンク・ジャンクション | 作業フォルダ内のフォルダを外部へのリンクやジャンクションに差し替えた状態で、復元・commit を行う。リンクをたどって外部に書き込まない |
| P-4 | ○ 作業フォルダの移動・改名・コピー | 作業フォルダごと移動・改名・コピーした後も、そのまま全操作ができる。コピーしたもの同士は互いに影響しない |
| P-5 | ○ サブフォルダからの実行 | 作業フォルダ内のサブフォルダから実行して、`.bvc` を見つけられる。`-C` による指定も同様に動く |
| P-6 | ○ 日本語・特殊な名前 | 日本語、空白、長いパス(Windows の260文字超。作業フォルダ自体が長い場合と、LongPathsEnabled が無効な場合を含む)、NFC と NFD の混在、絵文字を含む名前を扱える |
| P-7 | ○ 大文字小文字 | Windows で `a.bin` → `A.bin` に名前を変えた場合、名前変更として正しく記録・復元される。大文字小文字だけが異なるパスの衝突はエラーになる |
| P-8 | ○ 読み取り専用・属性 | 読み取り専用属性の付いたファイルを復元・削除できる(またはロールバックして明確なエラーになる) |
| P-9 | ○ フォルダの増減 | 版の間でサブフォルダが増えたり減ったりしても復元できる。空になったフォルダは残す |
| P-10 | ○ 別OS | Windows で作ったリポジトリを Linux で開いても、パス区切りの違いで壊れない(将来、リポジトリを共有する場合に備えて) |

## 3. データの破損・欠損

| # | 観点 | 確認内容 |
|---|---|---|
| C-1 | ◎ 破損後のコミット | チャンクを削除する、1バイト反転する、切り詰める、codec ID を書き換える。その後、作業ファイルを編集して commit し、新しい版へ goto すると正しく復元できる。変更していないファイルの未変更扱い(stat キャッシュ)を経由する場合も確認する |
| C-2 | ◎ 壊れた版を飛び越える | 版 5 を壊した状態で、@ = 7 から undo すると中止し、作業ファイルは変わらない。`undo --skip-broken` と `goto 3` では、版 3 に戻れる。版 5 への goto・redo は中止される |
| C-3 | ○ 壊れた版ファイル | commits/5.json を壊しても、log が表示でき(5 は ✗)、6 以降から 4 以前へたどれる(ancestors による) |
| C-4 | ○ 壊れたマニフェスト | 壊れたファイルを含む版だけが壊れた版になり、同じマニフェストを共有していない他の版は健全なまま |
| C-5 | ○ 隔離 | 検出した破損データが quarantine/ に移動し、以後の重複排除で再利用されない |
| C-6 | ○ repair | 作業ファイルに同じ内容がある場合、verify --repair で修復され、壊れていた版が健全に戻る |
| C-7 | ○ 管理ファイルの破損 | HEAD、counters、index、branches、health を、削除、空にする、不正な JSON にする。いずれの場合も自動で復旧し、作業ファイルは変わらない。config の破損は明確なエラーになる。読み込み自体が失敗した(使用中など)場合は、復旧せずに中止し、ファイルは変わらない |
| C-8 | ○ JSONL の破損 | oplog、notes、discarded の途中行や最終行が壊れていても、読み飛ばして動作する。最終行の残骸は、次の追記の後は途中行として警告される(消さない) |
| C-9 | ○ 復号サイズの制限 | 小さなチャンクファイルを、展開すると巨大になるデータ(zip爆弾)に差し替えても、メモリを使い果たさずに破損として検出される |
| C-10 | ○ 潜在的な破損(commit_verify) | `exists` では検出されない破損が、`full` の設定や verify では検出されることを確認する(既定値の限界を把握しておくため) |
| C-11 | ○ 同じ内容の偽データ | チャンクの中身を別のデータに差し替えてハッシュを合わせない場合、名前との照合で検出される |

## 4. 障害・中断

| # | 観点 | 確認内容 |
|---|---|---|
| R-1 | ○ commit 中の中断 | 各書き込み段階(チャンク、マニフェスト、counters、版、HEAD、bvc.lock、index、oplog)で例外や kill を起こす。再実行後、版の整合性が保たれ、verify が通る |
| R-2 | ○ 復元中の中断 | journal の staging、swapping の各件数目、swapped の各段階で kill する。次のコマンドで「全部元通り」か「完了」のどちらかになり、作業ファイルが中途半端な状態にならない。自動コミットを伴う移動がロールバックされた場合は、HEAD が auto を指し、作業フォルダが clean で、次の commit が新しいブランチを作らない |
| R-3 | ○ recover 中の中断 | recover 自体を途中で kill しても、再度の recover で収束する(冪等性) |
| R-4 | ○ ファイル使用中 | 他のプロセスがファイルを開いたまま(Windows の排他)で復元すると、ロールバックされ、終了コード3になる |
| R-5 | ○ 書き込み中のファイル | commit 中に別のプロセスがファイルに追記し続けると、再試行したうえで中止する |
| R-6 | ○ 容量不足 | 空き容量が足りない場合、commit と復元のどちらも、事前検査か書き込み失敗の時点で中止し、ゴミ以外を残さない |
| R-7 | ○ 二重起動とロック | 2つのプロセスが同時に実行するとロックで片方が止まる。残ったロックファイルがある場合は案内が表示される |
| R-8 | ○ gc 中の中断 | gc の途中で kill しても、有効な版はすべて復元できる |
| R-9 | ○ 更新日時を保った書き換え | サイズと更新日時を変えずに中身を書き換えた状態で undo・goto すると、その内容が自動コミットに保存され、失われない |
| R-10 | ○ 追跡対象外との衝突 | 追跡パターンから外したファイルが、移動先の版の書き出し先にある場合は中止し、そのファイルは変わらない |
| R-11 | ○ 確認と退避の間の書き換え | 自動コミットの後、退避の前にアプリがファイルを書き換えた場合は、中止してロールバックする |

## 5. 性能・規模

| # | 観点 | 確認内容 |
|---|---|---|
| S-1 | ○ サイズの境界 | 0バイト、1バイト、チャンクサイズちょうど、その±1、4GB超のファイルを往復できる |
| S-2 | ○ 規模 | 追跡ファイル0件、100件以上、版1,000以上で、log・commit・load の時間が許容範囲に収まる |
| S-3 | ○ メモリ | 数GBのファイルの commit・復元で、メモリ使用量がファイルサイズに比例しない |
| S-4 | ○ 未変更の高速判定 | 変更の無い commit・log が、ファイルを読まずに終わる(stat のみ) |
| S-5 | ○ 更新日時の限界 | 同じサイズで更新日時も同じまま内容が変わった場合は、検出できないことを確認する(既知の制約として記録。要件定義書 T-6) |
| S-6 | ○ 重複排除の効果 | 一部を上書きしたファイル、途中に挿入したファイルで、fixed・gear・whole の増分容量が期待通りになる |
| S-7 | ○ 巨大チャンクのメモリ | whole で数GBのファイルを保存・復元しても、メモリ使用量が一定に収まる |

## 6. git 連携

| # | 観点 | 確認内容 |
|---|---|---|
| G-1 | ○ bvc.lock の更新 | commit・undo・goto のたびに、内容が正しく更新される。キーの順序が安定していて、差分が最小になる |
| G-2 | ○ checkout 連動 | git checkout で過去のコミットに戻すと、バイナリも対応する版になる。未コミットの変更は自動コミットで保存される |
| G-3 | ○ pre-commit | snapshot モードと reject モードの動作。bvc.lock をステージし忘れた場合に警告が出る |
| G-4 | ○ gc の保護 | pin された版、git の全ブランチ・stash・reflog で参照される版が gc で消えない。git が失敗したときは何も消さない。`--no-git` のときだけ保護を省く |
| G-5 | ○ データが無い場合 | gc 済み、存在しない番号、別のリポジトリの bvc.lock、手で編集した bvc.lock、一部のデータだけが欠けた bvc.lock で sync すると、明確なエラーになり、作業ファイルは一切変わらない。非同期状態の警告が出る |
| G-8 | ○ 不正な bvc.lock のコミット拒否 | 上記の bvc.lock をステージして git commit すると、pre-commit で拒否される |
| G-9 | ○ 番号と内容の食い違い | bvc_commit の番号の版と内容が異なる場合は、内容を基準に動作し、警告が出る |
| G-6 | ○ 既存フック | 既存のフックを上書きしない |
| G-7 | ○ git が無い環境 | git 連携が無効なら、git が無くても全機能が動く |
| G-10 | ○ bvc.lock の無いコミット | bvc.lock をまだ作っていない、または削除したコミットへ git checkout しても作業ファイルは変わらない。その間に bvc の操作をしても bvc.lock を作り直さず、bvc.lock のあるブランチへ戻る git checkout が拒否されない。戻った後は sync でそのコミットの版になる |

## 7. 互換性(将来)

| # | 観点 | 確認内容 |
|---|---|---|
| V-1 | ◎ 旧形式の読み込み | 各バージョンで作ったリポジトリを保存しておき(テスト用フィクスチャ)、新しいバージョンで全ての版が復元・verify できる |
