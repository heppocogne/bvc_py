## 1. 全体構成

### 1.1 モジュールと依存関係

依存は上から下への一方向のみとする。

```
cli.py        引数解析・表示整形・終了コード・--json
  │
repo.py       各操作の手順(トランザクションの組み立て)
  │
  ├─ history.py    版のグラフ・HEAD・ブランチ・削除印・pins・操作ログ
  ├─ worktree.py   追跡ファイルの走査・stat キャッシュ・変更検出・復元トランザクション
  ├─ gitlink.py    bvc.lock・フック・git 履歴の走査(subprocess で git を呼ぶ)
  │
store.py      チャンク・マニフェストの保存/取得/検証
  ├─ chunkers.py   Chunker 実装(fixed, gear, whole)とレジストリ
  └─ codecs.py     Codec 実装(raw, zlib)とレジストリ
  │
fsutil.py     原子的書き込み・JSONL 追記/読込・ロック・パス照合(glob)
model.py      dataclass 定義(全層共通)
errors.py     例外定義(全層共通)
```

- chunker と codec の種類を知っているのは store だけ。他の層は設定値(dict)を渡すだけにする。
- 作業フォルダのパス(`workdir`)とリポジトリのパス(`repodir`)は、Repo が別々に持つ(将来の分離に備える)。

### 1.2 配布形態

- 開発はパッケージ `bvc/` として行う。
- 配布時は標準ライブラリの `zipapp` で `bvc.pyz` の1ファイルにまとめる。
- Windows 向けには `bvc.cmd`(`python "%~dp0bvc.pyz" %*`)を添える。

### 2.1 書き換えの分類

| 分類 | ファイル | 方法 |
|---|---|---|
| 不変 | commits, manifests, chunks | 新規作成のみ(原子的に書き込み) |
| 追記 | notes, discarded, pins, oplog | JSONL の末尾に追記し、fsync する |
| 置換 | HEAD, counters, branches, index, config, health, lockstate | 原子的に置き換える |

JSONL を読むときは、最終行が壊れていたら(書き込み途中で強制終了した場合)無視する。

### 2.2 チャンク `chunks/ab/<sha256>`

```
[1バイト: codec ID][ペイロード]
  codec ID: 0 = raw, 1 = zlib
```

- 名前は**圧縮前のデータ**の SHA-256(16進64桁)。先頭2桁をサブフォルダにする。
- 同じ名前のファイルがすでにあれば書かない(重複排除)。

### 2.3 マニフェスト `manifests/ab/<sha256>.json`

```json
{"format":1,"size":1073741824,"sha256":"<ファイル全体>",
 "chunker":{"name":"fixed","size":4194304},
 "chunks":[["<sha>",4194304],["<sha>",4194304]]}
```

- 正規化 JSON(`sort_keys=True`, `separators=(",",":")`, `ensure_ascii=False`, UTF-8)の SHA-256 を名前にする。
- `chunker` は記録用で、復元には使わない(チャンクを順に連結するだけ)。このおかげで分割方式を差し替えられる。
- 空ファイルは `chunks: []`。

### 2.4 版 `commits/<id>.json`

```json
{"format":1,"id":8,"parent":7,"ancestors":[7,5,3,0],"branch":3,
 "time":"2026-09-25T20:10:00+09:00",
 "kind":"commit",
 "message":"メッシュを細分化",
 "tree":{"model.bin":"<manifest sha>","mesh/a.dat":"<manifest sha>"},
 "renames":[["a.bin","b.bin",0.87]],
 "stats":{"new_bytes":54525952,"total_bytes":1073741824}}
```

- `kind` は `init` / `commit` / `auto` / `import` のいずれか。
- `parent` は作成時点の親で、変更しない。discard によるつなぎ直しは、読み込み時に計算する(4.4節)。
- `ancestors` は、作成時点の祖先(親から根まで)の番号の列。親の版ファイルが壊れて読めなくなっても、それより前の祖先をたどれるようにするための冗長情報。数千版でも数十KBに収まる。
- `tree` のキーは作業フォルダからの相対パス(区切り `/`、NFC 正規化、見つかったときの大文字小文字を保持)。

### 2.5 index.json(stat キャッシュ)

```json
{"format":1,"entries":{"model.bin":{"size":1073741824,"mtime_ns":1727262600000000000,"manifest":"<sha>"}}}
```

作業ファイルと、それに対応するマニフェストの組を覚える。無くなっても再計算できるので、壊れていたら捨てて作り直す。

### 2.6 その他の JSONL

```
notes/8.jsonl     {"time":"…","text":"収束せず"}
discarded.jsonl   {"time":"…","id":6}
pins.jsonl        {"time":"…","git":"<40桁>","bvc":8,"tree_hash":"<sha>"}
oplog.jsonl       {"time":"…","op":"undo","args":{…},"reason":"…",
                   "before":{"at":8,"branch":3},"after":{"at":7,"branch":3},
                   "created":[9],"result":"ok"}
```

### 2.7 health.json

```json
{"format":1,
 "bad_chunks":{"<sha>":{"time":"…","reason":"hash_mismatch"}},
 "bad_manifests":{"<sha>":{"time":"…","reason":"unreadable"}},
 "bad_commits":{"6":{"time":"…","reason":"json_error"}}}
```

- 壊れた版の判定は、この記録と版の tree から都度計算する(版ごとの状態は保存しない)。
- 修復や gc で解消したものは、記録から消す。
- このファイルが壊れた場合は空で作り直す。次の verify で再検出される。

### 2.8 形式番号と互換性

- 版・マニフェスト・各 JSON・JSONL の各行に `format` を持たせる。チャンクはヘッダの codec ID が同じ役割を担う。
- 読み込み時に、知らない format や codec ID を見つけたら、`UnsupportedFormat` で中止する。書き込みは一切しない。
- 形式を変えるときは、読み込み側に旧形式の読み込みを残し、変換は明示的な `migrate` コマンドで行う(将来対応)。

### 3.2 chunkers.py

```python
class Chunker(ABC):
    name: ClassVar[str]
    def __init__(self, **params): ...
    def params(self) -> dict: ...                          # マニフェストに記録
    def split(self, f: BinaryIO) -> Iterator[tuple[bytes, bool]]: ...
        # (断片, チャンク終端か) を逐次返す。断片は最大 16MiB
        # チャンクが断片より大きくても、メモリに全体を載せずに済む

class FixedChunker(Chunker):  name = "fixed"   # params: size
class GearChunker(Chunker):   name = "gear"    # params: min, avg_bits, max, seed
class WholeChunker(Chunker):  name = "whole"   # params: なし。ファイル全体を1チャンクにする

CHUNKERS: dict[str, type[Chunker]]
def make_chunker(spec: dict) -> Chunker
```

- `split` は、読み込み単位(例: 16MiB)でファイルを読みながら切り出す。メモリ使用量は、読み込み単位の定数倍に収める。
- whole では、チャンクの SHA-256 がファイル全体の SHA-256 と一致する。
- どの chunker を使うかは、`config.rules` をパスに照合して決める(worktree が store に spec を渡す)。
- Gear のテーブルは、seed から標準ライブラリの `random.Random` で生成する。seed を params に含めて再現性を持たせる。

### 3.4 store.py

```python
class ObjectStore:
    def __init__(self, repodir: Path, compression: str, threads: int): ...
    def has_chunk(self, sha: str, check: str = "exists") -> bool
        # check="exists": ファイルがあり、ヘッダの codec ID が既知で、隔離記録に無い
        # check="full"  : さらに読み出して復号し、ハッシュを照合する
        # 異常を見つけたら隔離して False を返す
    def put_chunk(self, data: bytes, check: str) -> ChunkRef   # スレッドセーフ
        # has_chunk(sha, check) が False なら、新しく書き込む
        # (隔離済み・欠損・破損のチャンクは、ここで作り直される)
    def put_chunk_stream(self, pieces: Iterable[bytes], codec: str, check: str) -> ChunkRef
        # 大きなチャンク用(stream_threshold = 64MiB 超、whole では常にこちら)
        # tmp に書きながら SHA-256 と zlib.compressobj を逐次適用し、
        # 最後に has_chunk を確認して、無ければハッシュ名へ os.replace、あれば tmp を捨てる
    def open_chunk(self, sha: str, length: int) -> Iterator[bytes]
        # 逐次に復号して断片を返す。最後にハッシュと長さを照合し、異常なら隔離して CorruptData
    def get_chunk(self, sha: str, length: int) -> bytes     # 小さなチャンク用(open_chunk の結合)
        # 復号+ハッシュ照合。復号後のサイズは length を上限にする
        # (zlib.decompressobj の max_length を使い、改ざんされたデータでのメモリ枯渇を防ぐ)
        # 異常なら隔離して CorruptData を送出
    def put_file(self, f: BinaryIO, chunker: dict, check: str,
                 progress: Callable | None = None) -> tuple[str, PutStats]
        # 読み込み(メイン) → split → ワーカーで hash+圧縮+書き込み
        # 全体 SHA-256 はメインで逐次計算。マニフェストを保存して sha を返す
    def hash_file(self, f: BinaryIO, chunker: dict) -> str
        # 保存せずにマニフェスト sha を計算(変更検出用)
    def get_manifest(self, sha: str) -> Manifest
        # 名前とのハッシュ照合、JSON と値の形式検査。異常なら隔離して CorruptData
    def manifest_ok(self, sha: str, check: str) -> bool
        # マニフェストと、その全チャンクが健全か
    def write_file(self, manifest_sha: str, out: BinaryIO) -> None
        # open_chunk を使ってチャンクを逐次に書き出し、全体 SHA-256 を照合(チャンクの大きさによらずメモリ一定)
    def quarantine(self, kind: str, sha: str, reason: str) -> None
    def iter_chunks(self) -> Iterator[str]; def iter_manifests(self) -> Iterator[str]
    def delete_chunk(self, sha: str); def delete_manifest(self, sha: str)
```

ファイル名に使うハッシュは、すべて `fsutil.check_sha()`(小文字16進64桁)を通してからパスに変換する。

## 4. 主要アルゴリズム

### 4.1 移動系コマンドの共通手順

```
lock → recover → リビジョン解決(移動先を先に確定)
→ touched = 現在の tree と移動先の tree で内容が異なるパス ∪ 移動先に無い、現在の追跡ファイル
→ 衝突検査: 移動先に書き出すパスに、追跡対象外のファイル・フォルダ・リンクがあれば SafetyAbort
→ state = worktree.state(@.tree, store_chunks=True, no_cache=touched)
     touched に含まれる作業ファイルは、stat キャッシュを使わずに必ずハッシュする
→ state.missing があり allow_missing でなければ SafetyAbort
→ state.dirty なら auto = history.new_commit(kind="auto", message="auto: before …"); @ = auto
→ 移動先の tree を決定
→ worktree.restore(target_tree, on_committed = HEAD 更新 + bvc.lock 更新)
     restore 内の退避直前にも、退避するファイルの stat が state 時点と同じか確認する
     (確認と退避の間にアプリが書き換えた場合に備えて)。異なれば中止してロールバック
→ oplog 追記 → unlock
```

移動先は自動コミットの**前に**解決する。例えば `@-` は、自動コミット作成前の @ を基準にする。

「保存されていない内容を上書き・削除しない」ことの保証は、次の3段構えで行う。

1. 触るファイルは必ずハッシュして、自動コミットで保存する。
2. 追跡対象外のファイルがある場所には書き出さない。
3. 退避する直前に、stat が変わっていないことを再確認する。

### 4.2 変更検出と保存(worktree.state / store.put_file)

1. `scan()` で追跡ファイルを列挙する。
2. 各ファイルについて、index の size と mtime_ns が一致すればマニフェストを再利用する。
3. 一致しないファイルは、stat₁ → 読み込み(split → ハッシュ →(保存))→ stat₂ の順に処理する。stat₁ ≠ stat₂ なら再試行し、3回失敗したら FileChanging。
4. 並列化の方式:
   - メインスレッドでファイルを読み、分割する。
   - `ThreadPoolExecutor(threads)` で SHA-256・存在確認・圧縮・書き込みを行う。
   - 処理中のチャンク数を `threads × 2` までに制限し、メモリ使用量を抑える。
   - hashlib と zlib は GIL を解放するので、スレッドで並列化できる。
5. 前の版の tree と比べ、modified・added・消えたものを求めてから、名前変更を検知する(4.3節)。

### 4.3 名前変更の検知

```
消えた集合 G、新しい集合 N
1. 手動指定(--rename)を確定し、G と N から除く
2. manifest.sha256 が一致する組を確定する(1対1。複数あればパスの辞書順で対応付け)
3. 残りについて sim(g, n) = |chunks(g) ∩ chunks(n)| のバイト数 / size(n) を計算する
   sim ≥ threshold の組を、sim の高い順に貪欲に確定する
4. 残った G を missing とする
5. missing ごとに、パターン外のファイルでサイズが一致するものを探す
   ハッシュが一致すれば hints に加える(作業フォルダ直下と同じフォルダのみ探す)
```

チャンクの集合は、マニフェストから取得できる(追加の読み込みは不要)。

### 4.4 つなぎ直し(effective_parent)

```
effective_parent(id):
    for p in chain(id):                 # 親 → 祖父 → … の順
        if p not in discarded and p in known_ids:
            return p
    return None

chain(id):
    版ファイルが読めれば commits[id].ancestors を返す
    読めない版は、子の ancestors に含まれる情報から祖先の列を補う
```

- 途中の版ファイルが壊れていても、子が持つ `ancestors` を使えば、それより前の祖先へたどれる。
- 読み込み不可の版も番号としてはグラフに残し、log では `✗` で表示する。
- 版の数は多くても数百なので、load 時に全ての版について計算しておく。子の一覧も同時に作る。

### 4.5 ブランチ規則とリビジョン解決

- **new_commit**: `children(@)` が空なら `branch = commits[@].branch`、空でなければ `branch = counters.next_branch++`。HEAD.branch を新しい版のブランチにする。
- **branch_tip(b)**: ブランチ b に属する生きている版のうち、最大の id。
- **redo**: `path = path_to_tip(HEAD.branch)`。@ が path 上にあれば、その1つ先端寄りの版へ進む。無ければ `children(@)` が1つのときだけそこへ進む。
- **undo**: `effective_parent(@)` へ移動する。HEAD.branch は変えない。
- **リビジョン式**: `atom ( '-' | '+' )*`。atom は `@`、版番号、ブランチ名のいずれか。ブランチ番号は内部IDで、リビジョン式には使わない。`+` は、HEAD.branch の経路上にあればその方向へ、そうでなければ子が1つの場合のみ進む。

### 4.6 復元トランザクション(全部成功か全部元通り)

作業域 `.bvc/txn/` は作業フォルダと同じボリュームにあるので、`os.replace` で原子的に移動できる。

```
0. 事前検査: target の全パスを検査(4.10節)し、全マニフェストの健全性を manifest_ok() で確認する
   → 壊れていれば BrokenVersion(何も変えずに中止)
   → write 対象の合計サイズ+余裕分の空き容量を shutil.disk_usage で確認し、足りなければ DiskFull
   journal.json を書く {"state":"staging","target":{…},"ops":[…]}
   ops: 各パスについて write(新内容を置く)/ delete(削除)/ keep(内容同一)
1. staging: write 対象を txn/new/<n> に展開する(全体 SHA-256 を照合し、fsync)
2. journal を "swapping" にする
3. 各 op を順に実行する
   - 現ファイルがあれば txn/old/<n> へ os.replace(退避)
   - write なら txn/new/<n> を本来の場所へ os.replace
   - 1件ごとに journal の done リストを更新する
   - 失敗(PermissionError 等)したら 5 へ
4. journal を "swapped" にし、on_committed()(HEAD・bvc.lock 更新)を実行する
   → index を更新し、txn/ を削除し、journal を削除する
5. ロールバック: done を逆順にたどり、old を元の場所へ戻し、new を削除する
   → txn/ を削除し、journal を削除し、FileBusy を送出する
```

**起動時の recover()**(journal が残っている場合)

| state | 処理 |
|---|---|
| staging | txn/ を削除する(作業ファイルには未着手) |
| swapping | done を逆順にロールバックする |
| swapped | on_committed() を再実行(冪等)してから後始末する |

- 退避したファイルは、自動コミットで保存済みか、現在位置の版と同一なので、ロールバックに失敗しても `.bvc` から復元できる。
- 復元に必要なフォルダは作る。削除で空になったフォルダは消さない(アプリが使っている可能性があるため)。

### 4.7 原子的書き込みと耐障害性

```python
def atomic_write(path, data):
    tmp = repodir/"tmp"/uuid
    write → flush → os.fsync → close → os.replace(tmp, path)
    POSIX ではディレクトリも fsync する(Windows では省略)
```

**commit の書き込み順**: チャンク → マニフェスト → counters → 版 → HEAD → bvc.lock → index → oplog。
どこで中断しても、版の書き込みより前なら参照されないゴミが残るだけになる。版の書き込み後に中断した場合は、HEAD が古いままの「子が1つ増えた状態」になるだけで、整合性は保たれる。

**ロック**: `os.open(lock, O_CREAT|O_EXCL)` で作成し、pid・時刻・ホスト名を書く。既にあれば Locked で中止し、内容を表示して、手動で削除する方法を案内する(stale 判定は行わない)。

### 4.8 gc(マーク&スイープ)

```
mark:
  版 = 生きている版 ∪ pins が指す版
  マニフェスト = 上記の版の tree の値
                ∪ (git 連携が有効なら、git の全履歴にある bvc.lock の manifest)
                ∪ 現在の bvc.lock の manifest
  チャンク = 上記マニフェストが参照するもの
sweep:
  commits/ のうち mark 外(削除済みかつ pin なし)→ 削除。notes も削除
  manifests/ と chunks/ のうち mark 外 → 削除
  tmp/ の残骸 → 削除
```

- 版のファイルを先に消し、次にマニフェスト、最後にチャンクを消す。途中で中断しても、残るのはゴミだけ。
- discarded.jsonl の記録は残す(番号は counters で管理するので再利用されない)。
- git の履歴は `git rev-list --all --reflog -- <lock_file>` でたどり、各リビジョンについて `git show <rev>:<path>` を読む(`--all` には stash も含まれる)。git が失敗した場合や、読めない bvc.lock があった場合は、何も削除せずに中止する。`--no-git` を指定したときだけ省略する。

### 4.9 verify

- 全チャンクを復号して SHA-256 を照合する。並列で行う。
- 全マニフェストについて、参照するチャンクが存在するか、長さの合計が size と一致するかを確認する。
- 生きている版と pin された版について、tree のマニフェストが存在するかを確認する。
- `--quick` では、存在確認と長さの確認だけを行う。
- 異常は隔離し、health.json に記録する。
- `--repair`: 壊れたチャンクの sha の集合 B を作る。現在の追跡ファイルと、パターン外で名前またはサイズが一致するファイルを、各版の chunker 設定で分割する。sha が B に含まれるチャンクが出てきたら put_chunk で保存し直す。修復できたものは health から消す。

### 4.10 パスの安全性(fsutil)

```python
def check_relpath(p: str) -> str
    # 2.9節(仕様書)の規則で検査し、NFC に正規化した相対パスを返す。不正なら UnsafePath
def resolve_in_workdir(workdir: Path, rel: str) -> Path
    # workdir/rel を組み立てたうえで、各親フォルダがシンボリックリンク・ジャンクションでないことを
    # os.lstat と stat.S_ISLNK / st_file_attributes(FILE_ATTRIBUTE_REPARSE_POINT)で確認し、
    # os.path.realpath の結果が workdir の内側にあることを確認する
def check_sha(s: str) -> str; def check_id(n) -> int
```

- 版・マニフェスト・bvc.lock・journal を読み込んだ直後と、作業ファイルへ書き込む・削除する直前の2か所で検査する(二重の防御)。
- 版の tree に不正なパスが含まれる場合、その版は壊れた版として扱う。load 時には例外にしない。
- `scan()` では `os.scandir` を使い、`follow_symlinks=False` でたどる。リンクとリパースポイントは対象外にする。

### 4.11 破損時の処理

**コミット時(新しい版が壊れたデータを参照しないようにする)**

- 変更のあったファイル: put_file で分割した各チャンクについて、`has_chunk(sha, check=commit_verify)` が False なら書き込む。隔離済み・欠損のものは、この時点で作業ファイルから作り直される。
- stat キャッシュで「未変更」とされたファイル: 再利用するマニフェストについて `manifest_ok(sha, check=commit_verify)` を確認する。False なら、そのファイルを未変更扱いにせず、再読み込みして put_file する。
- `commit_verify=exists` の場合、隔離も検出もされていない潜在的な破損(ビット化け)は見逃す。これは既定の性能とのトレードオフで、`full` にするか、定期的に verify を実行して対処する。

**移動時**

- 移動先の版を事前検査で確認する(4.6節の0)。壊れていれば、作業ファイルを変えずに BrokenVersion で中止する。
- `--skip-broken`: undo なら effective_parent を、redo なら先端方向の子を順にたどり、最初の健全な版を移動先にする。見つからなければ中止する。
- 事前検査を通っても、staging 中の照合で破損が見つかった場合は、隔離して staging を破棄し、BrokenVersion で中止する(作業ファイルは未着手)。

### 4.12 管理ファイルの自動復旧

`Repo.open()` の中で、各管理ファイルを読み込む際に検査する。

| ファイル | 異常時の処理 |
|---|---|
| index.json | 空として扱う。全追跡ファイルを再ハッシュすることになる |
| counters.json | max(版の番号, discarded の番号, oplog の created) + 1 で再計算する |
| HEAD.json | oplog の最後の after → 作業ファイルの tree_hash と一致する版 → 最新の版、の順に決める |
| branches.json | 空で作り直す |
| health.json | 空で作り直す |
| config.json | 自動復旧せず、BvcError で中止する |

いずれも警告を出したうえで、oplog に `{"op":"recover_control", …}` を記録する。

## 5. git 連携(gitlink.py)

| 関数 | 内容 |
|---|---|
| `write_lock(tree, commit_id)` | bvc.lock を正規化 JSON で原子的に書く |
| `read_lock(path \| git_rev)` | bvc.lock を読む |
| `tree_hash(tree)` | tree を正規化した SHA-256。版の同一判定と pins に使う |
| `find_commit_by_tree(tree)` | 内容が同じ生きている版を探す(bvc_commit のヒントを優先) |
| `install_hooks()` | フックを設置する |
| `lock_manifests_in_history()` | gc 用 |
| `check_staged_lock()` | pre-commit 用。`git show :<lock_file>`(ステージされた内容)を読み、全マニフェストが健全な版と一致するか確認する |

**非同期状態の記録**: bvc が最後に書いた bvc.lock の tree_hash を `.bvc/lockstate.json` に保存する。作業ツリーの bvc.lock が、この値とも @ の tree とも一致しなければ、非同期状態とみなす(git checkout の後に sync が失敗した、手で編集した、など)。非同期状態では、bvc.lock を上書きする操作の前に警告を表示し、その内容を oplog に記録する。

フック(`.git/hooks/pre-commit` など)の中身は、`sh` から Python を呼ぶだけにする。Git for Windows でも動く。

```sh
#!/bin/sh
exec python "<bvc.pyz のパス>" -C "<作業フォルダ>" git pre-commit
```

## 6. 性能と容量の見積もり

| 処理 | 1GB あたり(検証環境) |
|---|---|
| 未変更ファイルの判定 | ほぼ0(stat のみ) |
| SHA-256 | 約1秒 |
| 固定長の分割 | 読み込み速度に依存(ほぼ無視できる) |
| gear CDC の分割(純Python) | 約100秒 ← CDC を選ぶ場合の課題 |
| zlib L1 圧縮 | 約25秒/スレッド数(新規チャンクのみ) |

- 1GB のファイルは、4MiB チャンクで256個になり、マニフェストは約20KB。
- 管理データは、10ファイル × 100版でも数十MB程度。
- 実データ量は、各版で新しく増えたチャンクの合計(圧縮後)。最悪の場合は、毎回全量(圧縮後)が増える。

## 7. テスト方針

テスト観点の一覧は「04_テスト観点.md」にまとめる。実装の方針は次の通り。

- **テスト基盤**: 標準ライブラリの `unittest` を使う。各テストで一時フォルダに作業フォルダを作り、終了時に削除する。
- **障害注入**: `fsutil` の原子的書き込み、`os.replace`、チャンクの書き込みに、指定の回数目で例外を送出するフックを用意する(テスト時のみ有効)。
- **強制終了**: subprocess で bvc を起動し、進捗コールバックを合図に kill する。その後、recover と verify で整合性を確認する。
- **破損の再現**: チャンクファイルの削除、1バイト反転、切り詰め、codec ID の書き換え。版・マニフェストの JSON の破壊や改ざん。
- **大容量**: スパースファイルや、疑似乱数で生成したファイルを使う。tracemalloc でメモリ使用量を確認する。
