## 1. 全体構成

### 1.1 モジュールと依存関係

依存は上から下への一方向のみとする。

```
cli.py        引数解析・表示整形・終了コード・--json
  │
repo.py       各操作の手順(トランザクションの組み立て)
  │
  ├─ history.py    版のグラフ・HEAD・ブランチ・削除印・pins・操作ログ
  ├─ worktree.py   追跡ファイルの走査・stat キャッシュ・変更検出・復元トランザクション
  ├─ gitlink.py    bvc.lock・フック・git 履歴の走査(subprocess で git を呼ぶ)
  │
store.py      チャンク・マニフェストの保存/取得/検証
  ├─ chunkers.py   Chunker 実装(fixed, gear, whole)とレジストリ
  └─ codecs.py     Codec 実装(raw, zlib)とレジストリ
  │
fsutil.py     原子的書き込み・JSONL 追記/読込・ロック・パス照合(glob)
model.py      dataclass 定義(全層共通)
errors.py     例外定義(全層共通)
```

- chunker と codec の種類を知っているのは store だけ。他の層は設定値(dict)を渡すだけにする。
- 作業フォルダのパス(`workdir`)とリポジトリのパス(`repodir`)は、Repo が別々に持つ(将来の分離に備える)。
- **パスの持ち方**:
  - 作業フォルダ・リポジトリ内のファイルは、すべて基準フォルダからの相対パス(`/` 区切り、`..` や `\` を使わない。仕様書 2.10節)で保持し、層の間でもこの文字列で受け渡す。
  - OS の API に渡す直前に `fsutil.os_path()` で実際のパスにする。問題の無い(短い)パスはそのまま使い、長いパスだけ `\\?\` 付きに変換する(ネットワークパスは `\\?\UNC\`)。LongPathsEnabled が無効な環境でも 260 文字を超えるパスを扱うためである(4.10節)。
  - 作業フォルダの外の場所を設定で指定する場合(将来の mirror など)は、絶対パスで書く。
- 設定ファイル(config.json)の読み込みと検査は repo.py が行う。`Config` dataclass は model.py に置き、下位層には `Config` か dict を渡す。
- `src/bvc/__main__.py` を置き、`python -m bvc` と zipapp の入口にする。`main.py` は cli を呼んで終了コードを返すだけにする。

### 1.2 配布形態

- 開発はパッケージ `bvc/` として行う。
- 配布時は標準ライブラリの `zipapp` で `bvc.pyz` の1ファイルにまとめる。
- Windows 向けには `bvc.cmd`(`python "%~dp0bvc.pyz" %*`)を添える。

M5 で具体化した点(`tools/build_pyz.py`、手順は `docs/build_pyz.md`):

- `src/bvc/` を一時フォルダに複製し(`__pycache__` は除く)、`bvc/__init__.py` を pyproject.toml の version を埋め込んだものに置き換える。zipapp の中では `importlib.metadata` で版数を取れないためである。
- アーカイブ直下の `__main__.py` は自前で置く(`sys.exit(main())`)。`zipapp.create_archive(main=...)` が作る入口は、`main()` の戻り値を終了コードにしないため使わない(使うと、どのエラーでも終了コード0になる)。
- 圧縮は deflate(`compressed=True`)にする。Python 3.14 で加わった zstd などは、古い Python では読めない。
- 先頭に `#!/usr/bin/env python3` を付ける(Linux/macOS で直接実行できるように)。
- `bvc.cmd` は `@echo off` / `python "%~dp0bvc.pyz" %*` / `exit /b %ERRORLEVEL%` の3行(CRLF)。PowerShell の `$LASTEXITCODE` と cmd の `%ERRORLEVEL%` に、bvc の終了コードがそのまま入る。
- ビルドスクリプトも Python 3.11 以降で動かす(`tomllib` で version を読む)。

## 2. データ構造(`.bvc/`)

```
.bvc/
  config.json          設定
  HEAD.json            {"format": 1, "at": 8, "branch": 3}
  counters.json        {"format": 1, "next_commit": 9, "next_branch": 4}
  branches.json        {"format": 1, "names": {"3": "細分化"}}   名前付きのものだけ
  index.json           stat キャッシュ
  commits/8.json       版(不変)
  manifests/ab/<sha>.json   ファイル単位のチャンク列(不変)
  chunks/ab/<sha>      チャンク本体(不変)
  notes/8.jsonl        コメント(追記のみ)
  discarded.jsonl      削除印(追記のみ)
  pins.jsonl           git 参照(追記のみ)
  oplog.jsonl          操作ログ(追記のみ)
  health.json          健全性の記録(壊れたチャンク・マニフェスト・版)
  lockstate.json       {"format": 1, "tree_hash": "<sha>" | null}  最後に書いた bvc.lock の tree_hash(git 連携時。null は bvc.lock が無い状態。5節)
  quarantine/          隔離した壊れたデータ
  txn/                 復元トランザクション作業域(new/<n>: 展開した新しい内容、old/<n>: 退避した作業ファイル)
  journal.json         復元トランザクションの記録(復元中だけ存在する。4.6節)
  tmp/                 書き込み途中の一時ファイル
  lock                 ロックファイル
```

### 2.1 書き換えの分類

| 分類 | ファイル | 方法 |
|---|---|---|
| 不変 | commits, manifests, chunks | 新規作成のみ(原子的に書き込み) |
| 追記 | notes, discarded, pins, oplog | JSONL の末尾に追記し、fsync する |
| 置換 | HEAD, counters, branches, index, config, health, lockstate, journal | 原子的に置き換える |

JSONL を読むときは、最終行が壊れていたら(書き込み途中で強制終了した場合)無視する。ここでいう最終行は「改行で終わっていない最後の行」である。

- 追記(`append_jsonl`)は、末尾が改行でなければ先に改行を足してから書く(新しい行が壊れた行とつながらないように)。そのため、強制終了の残骸の行は、次の追記のあとは「途中の壊れた行」になり、読むたびに警告が出る(読み飛ばして動作は続ける)。JSONL は追記のみで書き換えない(K-2)ので、残骸は消さない。

### 2.2 チャンク `chunks/ab/<sha256>`

```
[1バイト: codec ID][ペイロード]
  codec ID: 0 = raw, 1 = zlib
```

- 名前は**圧縮前のデータ**の SHA-256(16進64桁)。先頭2桁をサブフォルダにする。
- 同じ名前のファイルがすでにあれば書かない(重複排除)。

### 2.3 マニフェスト `manifests/ab/<sha256>.json`

```json
{"format":1,"size":1073741824,"sha256":"<ファイル全体>",
 "chunker":{"name":"fixed","size":4194304},
 "chunks":[["<sha>",4194304],["<sha>",4194304]]}
```

- 正規化 JSON(`sort_keys=True`, `separators=(",",":")`, `ensure_ascii=False`, UTF-8)の SHA-256 を名前にする。
- `chunker` は記録用で、復元には使わない(チャンクを順に連結するだけ)。このおかげで分割方式を差し替えられる。
- 空ファイルは `chunks: []`。

### 2.4 版 `commits/<id>.json`

```json
{"format":1,"id":8,"parent":7,"ancestors":[7,5,3,0],"branch":3,
 "time":"2026-09-25T20:10:00+09:00",
 "kind":"commit",
 "message":"メッシュを細分化",
 "tree":{"model.bin":"<manifest sha>","mesh/a.dat":"<manifest sha>"},
 "renames":[["a.bin","b.bin",0.87]],
 "stats":{"new_bytes":54525952,"total_bytes":1073741824}}
```

- `kind` は `init` / `commit` / `auto` / `import` のいずれか。
- `parent` は作成時点の親で、変更しない。discard によるつなぎ直しは、読み込み時に計算する(4.4節)。
- `ancestors` は、作成時点の祖先(親から根まで)の番号の列。親の版ファイルが壊れて読めなくなっても、それより前の祖先をたどれるようにするための冗長情報。数千版でも数十KBに収まる。
- `tree` のキーは作業フォルダからの相対パス(区切り `/`、NFC 正規化、見つかったときの大文字小文字を保持)。

### 2.5 index.json(stat キャッシュ)

```json
{"format":1,"fs_time_ns":1727262605000000000,
 "entries":{"model.bin":{"size":1073741824,"mtime_ns":1727262600000000000,"manifest":"<sha>"}}}
```

作業ファイルと、それに対応するマニフェストの組を覚える。無くなっても再計算できるので、壊れていたら捨てて作り直す。

- `fs_time_ns` は、この index を作った走査の**開始時点**の、ファイルシステム上の時刻。走査の開始時に `.bvc/tmp/` へ空の目印ファイルを作り、その `st_mtime_ns` を読んで削除する。OS の時計ではなく、作業ファイルの更新日時と同じ時計(同じボリューム)で測るためである。
- 更新日時の粒度内の書き換えを見逃さないために使う(4.2節の手順2)。

### 2.6 その他の JSONL

```
notes/8.jsonl     {"format":1,"time":"…","text":"収束せず"}
discarded.jsonl   {"format":1,"time":"…","id":6}
pins.jsonl        {"format":1,"time":"…","git":"<40桁>","bvc":8,"tree_hash":"<sha>"}
oplog.jsonl       {"format":1,"time":"…","op":"undo","args":{…},"reason":"…",
                   "before":{"at":8,"branch":3},"after":{"at":7,"branch":3},
                   "created":[9],"result":"ok"}
```

JSONL は行ごとに `format` を検査する。知らない format の行は、壊れた行とは区別し、`UnsupportedFormat` で中止する(読み飛ばさない)。

### 2.7 health.json

```json
{"format":1,
 "bad_chunks":{"<sha>":{"time":"…","reason":"hash_mismatch"}},
 "bad_manifests":{"<sha>":{"time":"…","reason":"unreadable"}},
 "bad_commits":{"6":{"time":"…","reason":"json_error"}}}
```

- 壊れた版の判定は、この記録と版の tree から都度計算する(版ごとの状態は保存しない)。
- 修復や gc で解消したものは、記録から消す。
- このファイルが壊れた場合は空で作り直す。次の verify で再検出される。

### 2.8 形式番号と互換性

各 JSON ファイル・JSONL・bvc.lock は、**ファイルごとに独立した format フィールド**を持つ。これにより、1つのファイル形式のみを段階的にアップグレードできる。チャンクはヘッダの codec ID(0=raw, 1=zlib)が同じ役割を担う。

**形式番号の一覧**

| ファイル | 説明 | format |
|---|---|---|
| `.bvc/config.json` | 設定 | 1 |
| `.bvc/HEAD.json` | 現在位置とブランチ | 1 |
| `.bvc/counters.json` | 次の版番号、ブランチ番号 | 1 |
| `.bvc/branches.json` | ブランチ名 | 1 |
| `.bvc/index.json` | stat キャッシュ | 1 |
| `.bvc/health.json` | 破損記録 | 1 |
| `.bvc/lockstate.json` | bvc.lock の tree_hash | 1 |
| `.bvc/journal.json` | 復元トランザクションの記録 | 1 |
| `.bvc/commits/N.json` | 版データ | 1 |
| `.bvc/manifests/SHA.json` | マニフェスト | 1 |
| `.bvc/notes/N.jsonl` | コメント | 1 |
| `.bvc/discarded.jsonl` | 削除印 | 1 |
| `.bvc/pins.jsonl` | git 対応 | 1 |
| `.bvc/oplog.jsonl` | 操作ログ | 1 |
| `bvc.lock` | git 連携用 | 1 |

**読み込み動作**

- 読み込み時に、知らない format や codec ID を見つけたら、`UnsupportedFormat` で中止する。書き込みは一切しない。
- JSONL を読むときは、各行の format を検査し、知らない format の行は `UnsupportedFormat` で中止する(読み飛ばさない)。

**形式の進化と互換性**

- 形式を変更するときは、読み込み側に**旧形式の読み込みも残す**。変更されたファイル形式のバージョンだけを上げる。例：config.json を変更した場合は format: 1 → 2 にするが、HEAD.json は format: 1 のまま。
- 複数の形式バージョンが混在する状況に対応させる。読み込み時には各バージョンのロジックを分岐させる。
- **変換は明示的な `migrate` コマンドで行う**(将来実装)。全ファイルを新形式へ段階的に移行する際に使用。

## 3. 主要インターフェイス

### 3.1 model.py(抜粋)

```python
@dataclass(frozen=True, slots=True)
class ChunkRef:  sha: str; length: int

@dataclass(frozen=True, slots=True)
class Manifest:
    size: int; sha256: str; chunker: dict; chunks: tuple[ChunkRef, ...]

@dataclass(frozen=True, slots=True)
class Commit:
    id: int; parent: int | None; branch: int; time: str
    kind: str; message: str; tree: dict[str, str]
    renames: tuple[tuple[str, str, float], ...]; stats: dict
    ancestors: tuple[int, ...]    # 親から根までの版番号(親が壊れても祖先をたどるための冗長情報)

@dataclass(slots=True)
class WorkState:          # 作業フォルダの状態
```

### 3.2 chunkers.py

```python
class Chunker(ABC):
    name: ClassVar[str]
    def __init__(self, **params): ...
    def params(self) -> dict: ...                          # マニフェストに記録
    def split(self, f: BinaryIO) -> Iterator[tuple[bytes, bool]]: ...
        # (断片, チャンク終端か) を逐次返す。断片は最大 16MiB
        # チャンクが断片より大きくても、メモリに全体を載せずに済む

class FixedChunker(Chunker):  name = "fixed"   # params: size
class GearChunker(Chunker):   name = "gear"    # params: min, avg, max, seed(avg は2の累乗のバイト数)
class WholeChunker(Chunker):  name = "whole"   # params: なし。ファイル全体を1チャンクにする

CHUNKERS: dict[str, type[Chunker]]
def make_chunker(spec: dict) -> Chunker
```

- `split` は、読み込み単位(例: 16MiB)でファイルを読みながら切り出す。メモリ使用量は、読み込み単位の定数倍に収める。
- whole では、チャンクの SHA-256 がファイル全体の SHA-256 と一致する。
- どの chunker を使うかは、`config.rules` をパスに照合して決める(worktree が store に spec を渡す)。
- Gear のテーブルは、seed から標準ライブラリの `random.Random` で生成する。seed を params に含めて再現性を持たせる。
- seed は利用者が設定で指定できる。`init --chunker gear` で指定が無ければ、init が `secrets.randbits(64)` で決めて config.json に保存する。
- init 後に config.json を手で編集して gear にし、seed を書かなかった場合は、設定エラーとして中止し、seed の書き方を案内する(config は自動で書き換えない)。
- seed を変えると境界が変わり、1回だけ重複排除が効かなくなる(chunker の変更と同じ)。
- ハッシュは 64bit の Gear ハッシュ(`fp = (fp << 1) + table[byte]`、64bit で切り捨て)。古いバイトが押し出されるので、境界は直近 64 バイトの内容だけで決まり、途中への挿入・削除の後も境界が元と揃う(再同期する)。分割点ごとにハッシュを 0 に戻す。
- 分割点の判定は、ハッシュの上位 `log2(avg)` ビットが全て 0 であること(avg が2の累乗でなければ設定エラー)。下位ビットは直近数バイトにしか依存しないので使わない。`min` 未満では分割せず(min の 64 バイト手前からハッシュを計算すればよい)、`max` に達したら強制的に分割する。平均のチャンクサイズは `min + avg` 付近になる。
- `split` は、分割点の断片に終端(True)を付けて返す。store はこの終端でチャンクを区切るので、付け忘れるとファイル全体が1チャンクになり、重複排除が効かない。
- `make_chunker` は、指定が不正(不明な name、項目の過不足、値の範囲外)なら `ValueError` を送出する。下位層は設定エラーの種類を知らないので、repo.py が設定の検査時に `make_chunker` を呼び、`ValueError` を設定エラー(`BvcError`、終了コード 1)に変換する(I-17)。

### 3.4 store.py

```python
class ObjectStore:
    def __init__(self, repodir: Path, compression: str, threads: int): ...
    def has_chunk(self, sha: str, check: str = "exists") -> bool
        # check="exists": ファイルがあり、ヘッダの codec ID が既知で、隔離記録に無い
        # check="full"  : さらに読み出して復号し、ハッシュを照合する
        # 異常を見つけたら隔離して False を返す
    def put_chunk(self, data: bytes, check: str) -> ChunkRef   # スレッドセーフ
        # has_chunk(sha, check) が False なら、新しく書き込む
        # (隔離済み・欠損・破損のチャンクは、ここで作り直される)
    def put_chunk_stream(self, pieces: Iterable[bytes], codec: str, check: str) -> ChunkRef
        # 大きなチャンク用(stream_threshold = 64MiB 超、whole では常にこちら)
        # tmp に書きながら SHA-256 と zlib.compressobj を逐次適用し、
        # 最後に has_chunk を確認して、無ければハッシュ名へ os.replace、あれば tmp を捨てる
    def open_chunk(self, sha: str, length: int) -> Iterator[bytes]
        # 逐次に復号して断片を返す。最後にハッシュと長さを照合し、異常なら隔離して CorruptData
    def get_chunk(self, sha: str, length: int) -> bytes     # 小さなチャンク用(open_chunk の結合)
        # 復号+ハッシュ照合。復号後のサイズは length を上限にする
        # (zlib.decompressobj の max_length を使い、改ざんされたデータでのメモリ枯渇を防ぐ)
        # 異常なら隔離して CorruptData を送出
    def put_file(self, f: BinaryIO, chunker: dict, check: str,
                 progress: Callable | None = None, path: str | None = None,
                 compression: str | None = None) -> tuple[str, PutStats]
        # 読み込み(メイン) → split → ワーカーで hash+圧縮+書き込み
        # 全体 SHA-256 はメインで逐次計算。マニフェストを保存して sha を返す
        # compression は config の rules による、ファイル単位の圧縮方式の上書き
    def hash_file(self, f: BinaryIO, chunker: dict) -> str
        # 保存せずにマニフェスト sha を計算(変更検出用)
    def get_manifest(self, sha: str) -> Manifest
        # 名前とのハッシュ照合、JSON と値の形式検査。異常なら隔離して CorruptData
    def manifest_ok(self, sha: str, check: str) -> bool
        # マニフェストと、その全チャンクが健全か
    def write_file(self, manifest_sha: str, out: BinaryIO) -> None
        # open_chunk を使ってチャンクを逐次に書き出し、全体 SHA-256 を照合(チャンクの大きさによらずメモリ一定)
    def quarantine(self, kind: str, sha: str, reason: str) -> None
    def iter_chunks(self) -> Iterator[str]; def iter_manifests(self) -> Iterator[str]
    def delete_chunk(self, sha: str); def delete_manifest(self, sha: str)
```

ファイル名に使うハッシュは、すべて `fsutil.check_sha()`(小文字16進64桁)を通してからパスに変換する。

M1 の実装で加えた・具体化した点:

- `has_chunk(sha, check, length=None)`: full の検査で length が分かれば長さも照合する。
- `put_chunk_stream(pieces, compression=None, check)`: 圧縮方針(auto / none / zlib)を渡す。auto は最初の断片で判断する。
- `put_manifest(m) -> str`: 同名のファイルが同じ内容なら書かない。違う内容なら隔離して書き直す。
- `build_manifest(f, chunker) -> Manifest`: 保存せずにマニフェストを組み立てる(`hash_file` はこの sha)。名前変更の検知(4.3節)でチャンクの集合を使うため。
- `verify_all(quick=False, progress=None) -> StoreVerifyResult`: store 単体の全件検証(4.9節の土台)。
- `put_file` の処理中のチャンクは threads×2 件に加えて合計 256MiB までに制限する(大きな fixed のチャンクサイズでもメモリを抑えるため)。
- 知らない codec ID は、壊れたデータとは区別して `UnsupportedFormat` で中止する(隔離もしない)。codec ID が既知で復号できない・ハッシュが合わないものは破損として隔離する。
- チャンク・マニフェストの読み込み中の `OSError`(使用中など)は破損の証拠ではないので、隔離せずにそのまま送出する(D-15)。ファイルが無い場合は欠損として記録する。
- `Health(repodir)`: `is_bad(kind, key)`, `records(kind)`, `mark(kind, key, reason)`, `clear(kind, key)`。kind は `bad_chunks` / `bad_manifests` / `bad_commits`。記録は変更のたびに原子的に書く。

M4 の実装で加えた点:

- `Health.problem`: 読み込み時の異常(`"missing"` / `"corrupt"` / `"invalid"`、無ければ None)。`Health.rebuild()` で書き直す(4.12節)。
- `verify_all` は、マニフェストが参照するチャンクが無ければ `missing` として記録する(隔離記録のみ)。`--quick` で長さが合わないチャンクは、名前(内容のハッシュ)と長さが両立しないので、チャンクの方を隔離する。
- `peek_manifest(sha) -> Manifest | None`: 表示用(log の `✗`)。隔離も記録もせずに読み、無い・壊れている・読めない場合は None。
- `repair_from(f, chunker, chunks, manifests) -> (直したチャンク, 直したマニフェスト)`: f を分割し(`build_manifest`)、chunks に含まれるチャンクを保存し直す。場所は1回目の分割で調べ、2回目に該当する範囲だけを逐次に読んで `put_chunk_stream(check="full")` で保存する(メモリ使用量は一定)。読み直す間に変わった内容は別の名前で保存されるだけ(参照されないゴミ)。分割結果のマニフェストの名前が manifests に含まれれば、それも保存し直す。

**health.json の管理**: store.py に `Health` クラスを置き、health.json の読み書きを任せる。チャンク・マニフェストの隔離時は store が記録する。壊れた版ファイルの記録(`bad_commits`)は、history が store の `Health` を通して書く。

```python
        # 4.6節の復元トランザクション。current は直前の state の結果(退避直前の stat 再確認に使う)
        # 置き換えが済んだら on_committed(head) で HEAD を更新する(head は journal にも記録する)
    def recover(self, on_committed: Callable[[Head], None]) -> None   # 中断した復元の後始末(Repo.open から呼ぶ)
    def update_index(self, tree: dict[str, str], fs_time_ns: int) -> None
        # fs_time_ns は tree を得た走査の開始時点(WorkState.fs_time_ns)。復元後は復元開始前の時刻(I-19)
```

- `Worktree(workdir, bvc_dir, …)` の workdir は `.bvc` のあるフォルダ。サブフォルダや `-C` から実行しても、探索で見つけたこのフォルダを基準にする(P-5)。
- 走査では作業フォルダ直下の `.bvc` に入らない。
- M4 で加えたもの: `check_index()` / `reset_index()`(4.12節)、`repair_candidates(names, sizes)`(4.9節の修復の材料。追跡ファイルと、追跡対象外でファイル名かサイズが一致する通常ファイル。リンクはたどらない)。

- 時間のかかる処理(commit・移動系・gc・verify)は、引数 `progress: Callable[[ProgressEvent], None] | None` を受け取る(GUI の進捗表示用)。M5 で `init` にも加えた。commit・init・移動系の自動コミットでは、`worktree.state(progress=...)` から `store.put_file` まで渡し、取り込むファイルごとに `ProgressEvent("put", 読んだバイト数, ファイルサイズ, パス)` を送る(stat キャッシュで読まないファイルは送らない)。
- 例外は `errors.py` にまとめる。
- `open` と `init` は、途中で失敗したらロックを解放してから例外を送出する。`init` の失敗時は、作ったばかりの `.bvc` だけを削除する。
- 情報・警告のメッセージは各モジュールの `logging.getLogger(__name__)` で出す。出力先(情報は stdout、警告以上は stderr、`-q` と `--json` では情報を出さない)は cli が設定する。コマンドの結果(log の表示、`--json`)は cli が stdout に書く。

### 3.9 cli.py(M5 で具体化したもの)

外部から見た形式は仕様書 2.11節。

```python
def run(argv=None) -> int                    # 解析 → コマンド → 終了コード。例外はここで終了コードに変える
def to_jsonable(obj) -> Any                  # --json の共通変換(dataclass → dict)
class ProgressView:                          # ProgressEvent を受けて標準エラーの1行に上書き表示する
    def __call__(self, ev: ProgressEvent) -> None; def clear(self) -> None
def format_progress(ev: ProgressEvent) -> str
def setup_logging(quiet=False, warnings: list[str] | None = None, progress: ProgressView | None = None)
```

- **--json の変換**: `to_jsonable` は、dataclass をフィールドと公開のプロパティ(`property` で、名前が `_` で始まらないもの)の dict にする。タプルは list、集合は並べ替えた list、`Path` は str、dict のキーは str にする。コマンドごとの変換は書かず、repo 層の結果をそのまま渡す(フィールドを増やせば JSON にも出る)。出力の直前に `changed` の有無を確かめ(無ければプログラムの誤り)、`warnings` を加える。
- **エラー**: `BvcError` は `type`(クラス名)・`exit_code`・`details` を JSON にする。`KeyboardInterrupt` は終了コード3、予期しない例外は終了コード1(`--json` でもトレースバックは標準エラーに書く)。
- **引数の誤り**: `argparse.ArgumentParser` を継承して `error()` で `UsageError` を送出する(サブコマンドのパーサも同じクラスになる)。`SystemExit` で抜けないので、`--json` でも JSON で返せる。解析に失敗した時点では引数を解釈できていないため、`--json` の有無は引数の並びに `--json` があるかで判断する。
- **警告の集め方**: 下位の層は今までどおり `logging` で警告を出す。`--json` では、`bvc` ロガーのハンドラを「警告以上をリストに集めるもの」だけにし、画面には何も書かない。集めたものを出力の `warnings` にする。
- **進捗**: 標準エラーが端末(`isatty()`)で、`-q`・`--json` でないときだけ `ProgressView` を作り、repo の各操作に `progress` として渡す。同じ段階・同じファイルの更新は `PROGRESS_INTERVAL`(0.1 秒)に1回に間引く。行は `\r` で上書きし、前の行より短ければ空白で埋める。端末の幅を超える場合は先頭を削る(末尾の量と割合を残す)。ログのハンドラに、書く前に進捗の行を消すフィルタを付ける。コマンドの終わり(`finally`)にも消す。
- **文字コード**: `run` の最初に、標準出力・標準エラーを `errors="replace"` に設定し直す(表せない文字で `UnicodeEncodeError` にしない)。表示に使う記号(`✗ ╯ ├ ┼ ─ │ ○ →`)は、出力先の文字コードで表せなければ代わりの文字にする(`_SYMBOL_FALLBACKS`。ログのハンドラと結果の表示の両方で行う)。`--json` は、出力先の文字コードが UTF-8 系でなければ `ensure_ascii=True` で書く。

## 4. 主要アルゴリズム

### 4.1 移動系コマンドの共通手順

```
lock → recover → リビジョン解決(移動先を先に確定)
→ touched = 現在の tree と移動先の tree で内容が異なるパス ∪ 移動先に無い、現在の追跡ファイル
→ 衝突検査: 移動先に書き出すパスに、追跡対象外のファイル・フォルダ・リンクがあれば SafetyAbort
→ state = worktree.state(@.tree, store_chunks=True, no_cache=touched)
     touched に含まれる作業ファイルは、stat キャッシュを使わずに必ずハッシュする
→ state.missing があり allow_missing でなければ SafetyAbort
→ state.dirty なら auto = history.new_commit(kind="auto", message="auto: before …")
     auto も通常の commit と同じ書き込み順(4.7節)で作り、HEAD を auto に更新してから復元に進む(I-18)
→ 移動先の tree を決定
→ worktree.restore(target_tree, on_committed = HEAD 更新 + bvc.lock 更新)
     (sync では、自動コミットの時点では bvc.lock を書かない。bvc.lock が合わせる先だから。
      import の版は自動コミットの後に作る。5節)
     restore 内の退避直前にも、退避するファイルの stat が state 時点と同じか確認する
     (確認と退避の間にアプリが書き換えた場合に備えて)。異なれば中止してロールバック
→ oplog 追記 → unlock
```

移動先は自動コミットの**前に**解決する。例えば `@-` は、自動コミット作成前の @ を基準にする。

自動コミットの時点で HEAD も auto に進めるのは、復元がロールバックされたときに、HEAD・履歴・作業フォルダが一致した状態(作業フォルダ = auto の tree)で終わるようにするためである。HEAD を元の @ のままにすると、auto が「@ の子」として孤立し、次の commit が意図しない新しいブランチになる。

「保存されていない内容を上書き・削除しない」ことの保証は、次の3段構えで行う。

1. 触るファイルは必ずハッシュして、自動コミットで保存する。
2. 追跡対象外のファイルがある場所には書き出さない。
3. 退避する直前に、stat が変わっていないことを再確認する。

**discard(現在位置)**: 移動先 = effective_parent(@) を先に決め(無ければ CannotMove。自動コミットも作らない)、上の手順で移動する。削除印(discarded.jsonl への追記)は、復元が成功した後、oplog の前に書く(`_move` の `on_done`)。

- 復元が失敗・ロールバックした場合は印を付けない。HEAD は自動コミット(あれば)または元の @ のままで、HEAD が削除済みの版を指すことはない。
- 復元の完了後、印を書く前に強制終了した場合は「親へ移動しただけ」の状態で終わる(もう一度 discard すればよい)。recover は印を書かない(`on_committed` は HEAD の更新だけ)。
- 自動コミットは @ の子として作られ、印を付けた後のつなぎ直しで親の子になる。移動後の HEAD.branch は自動コミットのブランチ(undo と同じ)。

### 4.2 変更検出と保存(worktree.state / store.put_file)

1. `scan()` で追跡ファイルを列挙する。
2. 各ファイルについて、index の size と mtime_ns が一致し、かつ `mtime_ns < index.fs_time_ns - 2秒` であれば、マニフェストを再利用する。
   - 後半の条件を満たさないエントリ(記録した走査の開始時点から見て、更新日時の粒度内に書き換えられた可能性があるもの)は、size と mtime_ns が一致してもハッシュし直す。2秒は FAT の更新日時の粒度に合わせた余裕である。
   - 新しい index の `fs_time_ns` は今回の走査の開始時点にする。今回再利用したエントリは前回の時点で条件を満たしているので、今回の時点でも満たす。今回ハッシュしたエントリは、今回の時点で判定し直される。
3. 一致しないファイルは、stat₁ → 読み込み(split → ハッシュ →(保存))→ stat₂ の順に処理する。stat₁ ≠ stat₂ なら再試行し、3回失敗したら FileChanging。
4. 並列化の方式:
   - メインスレッドでファイルを読み、分割する。
   - `ThreadPoolExecutor(threads)` で SHA-256・存在確認・圧縮・書き込みを行う。
   - 処理中のチャンク数を `threads × 2` までに制限し、メモリ使用量を抑える。
   - hashlib と zlib は GIL を解放するので、スレッドで並列化できる。
5. 前の版の tree と比べ、modified・added・消えたものを求めてから、名前変更を検知する(4.3節)。

### 4.3 名前変更の検知

```
消えた集合 G、新しい集合 N
1. 手動指定(--rename)を確定し、G と N から除く
2. manifest.sha256 が一致する組を確定する(1対1。複数あればパスの辞書順で対応付け)
3. 残りについて sim(g, n) = |chunks(g) ∩ chunks(n)| のバイト数 / size(n) を計算する
   sim ≥ threshold の組を、sim の高い順に貪欲に確定する
4. 残った G を missing とする
5. missing ごとに、パターン外のファイルでサイズが一致するものを探す
   ハッシュが一致すれば hints に加える(作業フォルダ直下と同じフォルダのみ探す)
```

チャンクの集合は、マニフェストから取得できる(追加の読み込みは不要)。

- **手動指定**: repo 層で `\` を `/` にし、先頭の `./` を除いて `check_relpath` で正規化する(不正なら `UsageError`)。worktree 層で G・N に対応付ける(完全一致、なければ大文字小文字を無視して一意に決まるもの)。対応先が無い・重複する指定は `UsageError` で中止する(D-15。推測で無視しない)。
- **完全一致**: まずマニフェストの名前(tree の値)が同じ組を読み込みなしで確定し、残りは `manifest.sha256`(内容全体のハッシュ)で比べる。rules で分割方式が変わった場合も一致させるため。
- **マニフェストの取得**: G 側は `get_manifest` で読み、`CorruptData` なら対応付けに使わない(OSError はそのまま送出)。N 側は、保存済みならそれを読み、無ければ(保存しない status のとき)ファイルから `build_manifest` で組み立て直し、名前が tree の値と一致するときだけ使う。保存されていないマニフェストを `get_manifest` で読むと「欠落」として隔離記録されるため、先に存在を確かめる(status に副作用を持たせない)。
- **決定性**: 集合の反復順に依存しないよう、候補はパスの辞書順に並べ、類似度の組は (sim の降順, g, n) で並べる。
- **ヒント**: 作業フォルダ直下と missing のあったフォルダの、追跡対象でない通常ファイル(リンクを除く)について、サイズが一致すれば内容全体の SHA-256 を計算し、`manifest.sha256` と比べる(分割方式に依存しない)。表示のためだけの情報なので、読めないファイルは飛ばす。`MissingFiles` の `details["hints"]` にも入れる。

### 4.4 つなぎ直し(effective_parent)

```
effective_parent(id):
    for p in chain(id):                 # 親 → 祖父 → … の順
        if p not in discarded and p in known_ids:
            return p
    return None

chain(id):
    版ファイルが読めれば commits[id].ancestors を返す
    読めない版は、子の ancestors に含まれる情報から祖先の列を補う
```

- 途中の版ファイルが壊れていても、子が持つ `ancestors` を使えば、それより前の祖先へたどれる。
- 読み込み不可の版も番号としてはグラフに残し、log では `✗` で表示する。
- 版の数は多くても数百なので、load 時に全ての版について計算しておく。子の一覧も同時に作る。

### 4.5 ブランチ規則とリビジョン解決

- **new_commit**: `children(@)` が空なら `branch = commits[@].branch`、空でなければ `branch = counters.next_branch++`。HEAD.branch を新しい版のブランチにする。
- **branch_tip(b)**: ブランチ b に属する有効な版のうち、最大の id。
- **redo**: `path = path_to_tip(HEAD.branch)`。@ が path 上にあれば、その1つ先端寄りの版へ進む。無ければ `children(@)` が1つのときだけそこへ進む。
- **undo**: `effective_parent(@)` へ移動する。HEAD.branch は変えない。
- **リビジョン式**: `atom ( '-' | '+' )*`。atom は `@`、版番号、ブランチ名のいずれか。ブランチ番号は内部IDで、リビジョン式には使わない。`+` は、HEAD.branch の経路上にあればその方向へ、そうでなければ子が1つの場合のみ進む。

### 4.6 復元トランザクション(全部成功か全部元通り)

作業域 `.bvc/txn/` は作業フォルダと同じボリュームにあるので、`os.replace` で原子的に移動できる。

```
0. 事前検査: target の全パスを検査(4.10節)し、全マニフェストの健全性を manifest_ok() で確認する
   → 壊れていれば BrokenVersion(何も変えずに中止)
   → write 対象の合計サイズ+余裕分の空き容量を shutil.disk_usage で確認し、足りなければ DiskFull
   journal.json を書く {"format":1,"state":"staging","target":{…},"ops":[…]}
   ops: 各パスについて write(新内容を置く)/ delete(削除)/ keep(内容同一)
1. staging: write 対象を txn/new/<n> に展開する(全体 SHA-256 を照合し、fsync)
2. journal を "swapping" にする
3. 各 op を順に実行する
   - 現ファイルがあれば txn/old/<n> へ os.replace(退避)
   - write なら txn/new/<n> を本来の場所へ os.replace
   - 1件ごとに journal の done リストを更新する
   - 失敗(PermissionError 等)したら 5 へ
4. journal を "swapped" にし、on_committed()(HEAD・bvc.lock 更新)を実行する
   → index を更新し、txn/ を削除し、journal を削除する
5. ロールバック: done を逆順にたどり、old を元の場所へ戻し、new を削除する
   → txn/ を削除し、journal を削除し、FileBusy を送出する
```

**起動時の recover()**(journal が残っている場合)

| state | 処理 |
|---|---|
| staging | txn/ を削除する(作業ファイルには未着手) |
| swapping | done を逆順にロールバックする |
| swapped | on_committed() を再実行(冪等)してから後始末する |

**M3 の実装で具体化した点**

- journal は `.bvc/journal.json` に置く(作業域 `txn/` の外。作業域を消してから journal を消す)。
  ```json
  {"format":1,"state":"swapping","head":{"at":0,"branch":0},"fs_time_ns":…,
   "target":{"a.bin":"<manifest sha>"},
   "ops":[{"n":0,"kind":"delete","path":"d/c.bin","src":"d/c.bin","sha":null,"expect":[2,…],"staged":null},
          {"n":1,"kind":"write","path":"a.bin","src":"a.bin","sha":"<sha>","expect":[6,…],"staged":[2,…]}],
   "done":1}
  ```
  - `ops` は keep を含めない。削除を先、書き出しを後に並べる(Windows で大文字小文字だけの名前変更をするとき、同じ実体を先に退避するため)。
  - `src` は退避する作業ファイルの実際の名前(無ければ null)、`expect` は state 時点のその (size, mtime_ns)、`staged` は `txn/new/<n>` に展開した内容の (size, mtime_ns)(os.replace で移しても変わらない)。
  - 読み込み時に、全パス(`check_relpath`。正規化で変わるものも不正)・ハッシュ・番号・stat を検査する。不正なら何も変えずに `CorruptData` で中止する(K-3、P-1)。
- 事前検査(`check_target`)は、自動コミットの前に Repo からも呼ぶ(衝突や壊れた版で中止するときに、自動コミットを作らないため)。restore の中でも state の結果を使ってもう一度行う。
  - 衝突の判定: 書き出し先とその途中のフォルダに既に何かがあり、それが追跡ファイル(同じ実体であることを `os.path.samestat` で確認)でなければ `SafetyAbort`。途中が「削除する追跡ファイル」なら衝突としない(先に削除してからフォルダを作る)。
- 退避の直前に加えて、退避した直後にも `txn/old/<n>` の stat を `expect` と比べる。確認から退避までの間に書き換えられた場合も、ロールバックして `FileChanging` で中止する(R-11)。
- **ロールバックは、ファイルの有無から各 op の進み具合を判断する**(done は参考情報)。逆順に、(1) `new/<n>` が無ければ、書き出した先の stat が `staged` と一致することを確かめて `new/<n>` へ戻し、(2) `old/<n>` があれば元の場所へ戻す。何度実行しても同じ結果になる(R-3)。stat が一致しない・戻す先に別のファイルがある場合は、何も上書きせずに中止する(D-15)。
- ロールバックが終わったら、journal を `staging`(作業ファイルは未着手)に書き換えてから作業域を消す。作業域を消している途中で中断しても、次の recover が `new/` の無い swapping を元に戻そうとしないようにするためである。
- ロールバック自体が失敗した場合は journal を swapping のまま残し、`FileBusy` で中止する(次のコマンドの recover で再試行する)。swapped の後の処理(HEAD・index の更新、後始末)が失敗した場合も journal を残し、次の recover で完了させる。
- 作業域の読み取り専用属性のファイル(退避した作業ファイル)は、属性を外してから削除する(P-8)。
- journal が無いのに作業域が残っている場合: `txn/new/` は消す。`txn/old/` は元のファイルの可能性があるので消さずに警告し、次の復元は中止する。
- 障害注入の段階名: `stage:<n>`(展開の後)、`replace:stash:<n>`・`replace:swap:<n>`(退避・書き出し)、`replace:unswap:<n>`・`replace:unstash:<n>`(ロールバック)、`txn_cleanup`、`remove:journal.json`。journal の書き込みは `atomic_write:journal.json`。
- 復元後の index の `fs_time_ns` には、直前の state の走査開始時点(自動コミットの index と同じ値)を使う。復元の開始より前の時刻なので I-19 を満たし、置き換えなかったファイルの記録も安全側になる。
- 移動系の oplog は、自動コミットを作った後に復元が失敗した場合も `result: "error"` で記録する(`created` に auto の番号)。

- **index の更新**: 復元が完了したら `update_index` で、復元後の stat を記録する。このときの `fs_time_ns` は、**復元を始める前**のファイルシステム上の時刻にする。復元したファイルの更新日時はそれ以降(T-10 の現案では復元時刻)になるので、次の走査で必ず1回ハッシュし直され、更新日時の粒度内の書き換えを見逃さない(4.2節、I-14)。
- 退避したファイルは、自動コミットで保存済みか、現在位置の版と同一なので、ロールバックに失敗しても `.bvc` から復元できる。
- 復元に必要なフォルダは作る。削除で空になったフォルダは消さない(アプリが使っている可能性があるため)。

### 4.7 原子的書き込みと耐障害性

```python
def atomic_write(path, data):
    tmp = repodir/"tmp"/uuid
    write → flush → os.fsync → close → os.replace(tmp, path)
    POSIX ではディレクトリも fsync する(Windows では省略)
```

**commit の書き込み順**: チャンク → マニフェスト → counters → 版 → HEAD → bvc.lock → index → oplog。
どこで中断しても、版の書き込みより前なら参照されないゴミが残るだけになる。版の書き込み後に中断した場合は、HEAD が古いままの「子が1つ増えた状態」になるだけで、整合性は保たれる。

**ロック**: `os.open(lock, O_CREAT|O_EXCL)` で作成し、pid・時刻・ホスト名を書く。既にあれば Locked で中止し、内容を表示して、手動で削除する方法を案内する(stale 判定は行わない)。

### 4.8 gc(マーク&スイープ)

```
mark:
  版 = 有効な版 ∪ pins が指す版
  マニフェスト = 上記の版の tree の値
                ∪ (git 連携が有効なら、git の全履歴にある bvc.lock の manifest)
                ∪ 現在の bvc.lock の manifest
  チャンク = 上記マニフェストが参照するもの
sweep:
  commits/ のうち mark 外(削除済みかつ pin なし)→ 削除。notes も削除
  manifests/ と chunks/ のうち mark 外 → 削除
  tmp/ の残骸 → 削除
```

- 版のファイルを先に消し、次にマニフェスト、最後にチャンクを消す。途中で中断しても、残るのはゴミだけ。
- discarded.jsonl の記録は残す(番号は counters で管理するので再利用されない)。
- git の履歴は `git rev-list --all --reflog -- <lock_file>` でたどり、各リビジョンについて `git show <rev>:<path>` を読む(`--all` には stash も含まれる)。git が失敗した場合や、読めない bvc.lock があった場合は、何も削除せずに中止する。`--no-git` を指定したときだけ省略する。

**M4 の実装で具体化した点**(git・bvc.lock の保護は M6)

- 消す版 = 削除印あり かつ pin なし かつ HEAD でない版。読み込み不可の版でも、削除印が無ければ残す。
- mark で参照先を把握できない場合は、その先の削除を見送る(D-15)。見送ったものは `GcReport.skipped` に入れ、警告を出す。
  - 残す版に `tree_known` でないもの(読み込み不可・不正なパス)がある → マニフェストとチャンクを消さない(版だけ消す)。
  - 残す版が参照するマニフェストが読めない(`CorruptData`)→ チャンクを消さない。読み込み自体の `OSError` は何も消さずに `FileBusy`。
- 削除順: 版ファイル(→ そのコメント)→ 版の無いコメント → マニフェスト → チャンク → tmp/ のファイル。マニフェストを消し終えてからチャンクを消すので、途中で止まっても、残っているマニフェストが消えたチャンクを参照することはない。消した版の health の `bad_commits` も消す。
- 削除の後は History を読み直してから oplog に記録する(`{"op":"gc", …, "deleted":{…}, "skipped":[…]}`)。削除対象が無ければ oplog に書かない。
- `--dry-run` は削除対象と容量を数えるだけで、何も書かない。ただし、mark の読み込み中に見つけたマニフェストの破損は、他の操作と同じく隔離される。
- 障害注入の段階名: `gc:commit`、`gc:note`、`gc:manifest`、`gc:chunk`、`gc:tmp`(各削除の直前)。

### 4.9 verify

- 全チャンクを復号して SHA-256 を照合する。並列で行う。
- 全マニフェストについて、参照するチャンクが存在するか、長さの合計が size と一致するかを確認する。
- 有効な版と pin された版について、tree のマニフェストが存在するかを確認する。
- `--quick` では、存在確認と長さの確認だけを行う。
- 異常は隔離し、health.json に記録する。
- `--repair`: 壊れたチャンクの sha の集合 B を作る。現在の追跡ファイルと、パターン外で名前またはサイズが一致するファイルを、各版の chunker 設定で分割する。sha が B に含まれるチャンクが出てきたら put_chunk で保存し直す。修復できたものは health から消す。

**M4 の実装で具体化した点**

```
before = health の記録
store.verify_all(quick)                 チャンクの照合・隔離、マニフェストの検査、欠損の記録
版ファイルの状態を bad_commits に記録   読めない → unreadable、tree が不正 → invalid_tree、正常なら消す
_check_versions(kept)                   kept = 有効な版 ∪ pin された版
    tree_known でない版 → 壊れた版
    tree のマニフェストを get_manifest(記録されていない欠損はここで記録)。読めなければ壊れた版
    マニフェストのチャンクを has_chunk(exists)。False なら壊れた版
repair なら _repair → 直せたら _check_versions をやり直す
changed = 修復した or health の記録が before と異なる
oplog に {"op":"verify", …, "broken":[…], "repaired":{…}}
```

- 削除済みの版(pin なし)だけが参照するデータの異常は、結果に含めない(gc で消える)。
- 修復の材料: 追跡ファイルすべてと、追跡対象外の通常ファイルのうち、ファイル名(大文字小文字を問わない)が「壊れたデータを参照する版の tree のファイル名」と一致するもの、またはサイズがその読めたマニフェストの size と一致するもの。作業フォルダ全体を探す(フォルダは問わない)。
- 分割方式: 設定の chunker、rules の chunker、読めたマニフェストに記録された chunker(重複は除く)。マニフェストが読めない場合も、同じ分割方式なら `repair_from` がマニフェストごと作り直せる。
- 異常が残っていても例外にはしない(repo 層は結果を返し、終了コード 1 は cli が決める)。

- 版の読み込み(`history._parse_commit`)では、tree のパスが `check_relpath` で変わる(NFC でない)場合も不正とする。NFC と NFD の2つのキーが1つにまとまって、片方が黙って消えるのを防ぐ。名前変更の記録(`renames`)も `[消えたパス, 新しいパス, 類似度(0〜1)]` の形とパスを検査し、不正なら壊れた版とする(表示にしか使わないが、記録されたパスは使う前に検査する原則に合わせる)。
- 予約名に `CONIN$`・`CONOUT$` を加えた(Python の `ntpath.isreserved` に合わせる)。なお Windows 11 では、フォルダ付きなら `CON` なども普通のファイルとして作れるが、以前の Windows との互換のため拒否のままとする。
- `os_path()` は作業ファイルだけでなく `.bvc` の中のパスにも通す(作業フォルダ自体が長い場合に必要)。M4-12 で、`Repo.find_workdir`・`Repo.init`(`.bvc` とその下のフォルダの作成、失敗時の削除)と `History` の `commits/` の走査・存在確認が素のパスだったのを直した。`Path.resolve()` と `Path.is_dir()` の代わりに `fsutil.real_path()`・`fsutil.is_dir()`(`os_path` を通してから `\\?\` を外す)を使う。
- ネットワークドライブ・subst のドライブで開いた場合、`Repo.workdir` は `realpath` の結果(ネットワークドライブなら UNC)になる。M4-12 の確認では、ローカルの管理共有・`net use`・subst のいずれでも誤って中止する例は無く、要件定義書 T-14(同じ場所とみなすパスの設定)は不要と判断した。

### 4.11 破損時の処理

**コミット時(新しい版が壊れたデータを参照しないようにする)**

- 変更のあったファイル: put_file で分割した各チャンクについて、`has_chunk(sha, check=commit_verify)` が False なら書き込む。隔離済み・欠損のものは、この時点で作業ファイルから作り直される。
- stat キャッシュで「未変更」とされたファイル: 再利用するマニフェストについて `manifest_ok(sha, check=commit_verify)` を確認する。False なら、そのファイルを未変更扱いにせず、再読み込みして put_file する。
- `commit_verify=exists` の場合、隔離も検出もされていない潜在的な破損(ビット化け)は見逃す。これは既定の性能とのトレードオフで、`full` にするか、定期的に verify を実行して対処する。

**移動時**

- 移動先の版を事前検査で確認する(4.6節の0)。壊れていれば、作業ファイルを変えずに BrokenVersion で中止する。
- `--skip-broken`: undo なら effective_parent を、redo なら先端方向の子を順にたどり、最初の健全な版を移動先にする。見つからなければ中止する。
- 事前検査を通っても、staging 中の照合で破損が見つかった場合は、隔離して staging を破棄し、BrokenVersion で中止する(作業ファイルは未着手)。

**M4 の実装で具体化した点**

- 「健全」の判定(`Repo._is_healthy`)は、版ファイルが読めて tree が正しく、全マニフェストについて `manifest_ok(check="exists")` が True であること。チャンクの中身までは読まない。移動先の判定は自動コミットの前に行うので、壊れた版で中止するときに自動コミットを作らない。
- `--skip-broken` でない場合は、移動先が壊れていれば BrokenVersion(`--skip-broken` の案内付き)。
- redo の先端方向: HEAD.branch の経路上ならその経路を、経路の外なら子が1つの間だけたどる(子が複数なら、飛ばした版を示して BrokenVersion)。移動後の HEAD.branch は、移動先が経路上なら HEAD.branch のまま、経路の外なら移動先の版のブランチ。
- 根での undo は `--skip-broken` でも CannotMove(終了コード 4)。飛ばした先に健全な版が無ければ BrokenVersion(何も変えない)。
- 飛ばした版は `MoveResult.skipped` と oplog の `args.skipped` に記録する。
- staging 中に見つかった破損は隔離の記録に残るので、次の `--skip-broken` では事前の判定で飛ばせる。

**log の `✗`**(M4-11): 版ファイルが読めない・tree が不正な版に加えて、health の記録にあるマニフェスト、または記録にあるチャンクを参照するマニフェスト(`peek_manifest` で読む)を使う版に付ける。log は検査も記録もしない。

### 4.12 管理ファイルの自動復旧

`Repo.open()` の中で、各管理ファイルを読み込む際に検査する。

| ファイル | 異常時の処理 |
|---|---|
| index.json | 空として扱う。全追跡ファイルを再ハッシュすることになる |
| counters.json | max(版の番号, discarded の番号, oplog の created) + 1 で再計算する |
| HEAD.json | oplog の最後の after → 作業ファイルの tree_hash と一致する版 → 最新の版、の順に決める |
| branches.json | 空で作り直す |
| health.json | 空で作り直す |
| config.json | 自動復旧せず、BvcError で中止する |

自動復旧は、ファイルが**無い・解析できない・形式が不正**(`FileNotFoundError` / `CorruptData`)のときだけ行う。読み込み自体の `OSError`(使用中など)は破損の証拠ではないので、何も変えずに `FileBusy` で中止する(D-15)。知らない `format` は `UnsupportedFormat` で中止する。

いずれも警告を出したうえで、oplog に `{"op":"recover_control", …}` を記録する。

**M4 の実装で具体化した点**

- `Repo.open` の手順: ロック → config.json(無い・壊れていれば、修正方法を案内して BvcError)→ journal の recover → `_recover_control`。この間の `OSError` は、何も変えずに `FileBusy` にしてロックを解放する。
- `_recover_control` の順序: branches.json(load の中で読むので先に直す)→ `History.load` → counters.json → HEAD.json → index.json → health.json → oplog への記録。異常を見つけたファイルは、その場で作り直す(次の open で同じ記録を繰り返さないため)。
- counters.json: `next_commit` = max(版ファイル・削除印・oplog の created と before/after の at)+ 1。`next_branch` = max(読める版のブランチ、branches.json の番号、oplog の before/after の branch)+ 1。gc で消えた版の番号も削除印と oplog に残るので再利用しない。
- HEAD.json: 存在しない版・削除済みの版を指している場合も異常とする。oplog の after は、after を持つ最後の記録だけを見る(その版が有効でなければ次の手段へ)。作業ファイルとの照合は `state(base_tree={}, store_chunks=False)` の tree と版の tree の一致で行い、新しい版を優先する。
- index.json: 空の index(`fs_time_ns: 0`)を書く。
- oplog の記録: `{"op":"recover_control","args":{"file":…,"problem":…,"action":…},"before":null,"after":<復旧後の HEAD>,…}`。

### 4.13 squash(版の統合)

子の版 X を親 P(effective_parent)に統合する(仕様書 3.14節、D-22)。版は不変なので、P・X を書き換えずに新しい版 N を作る。

```
lock → recover → X = resolve(rev)、P = effective_parent(X)
→ 事前検査(何も変えない):
     P が無い → CannotMove / X に有効な子がある → BvcError / HEAD.at == P → BvcError
     P・X が読めない、X が健全でない(_is_healthy)→ BrokenVersion
     P・X が pin されていて force でない → PinnedCommit
→ N = history.new_commit(parent=effective_parent(P), tree=X.tree, kind="commit",
                         message, renames=つないだもの, branch=X.branch)
→ P・X のコメントを、元の日時のまま N に追記する
→ HEAD.at == X なら HEAD = (N, N.branch)、bvc.lock を更新(内容は同じなので書き換わらない)
→ discard(P) → discard(X) → oplog("squash", created=[N])
```

- **ブランチ**: ブランチ規則に任せると、P の親には P という子があるので新しいブランチになり、X のブランチの名前が付いていかない。`new_commit(branch=...)` で X のブランチを指定する。N は最も新しい番号なので、そのブランチの先端になる。
- **作業ファイル**: N の tree は X と同じなので、復元も自動コミットもしない。index も変えない(tree が同じため)。
- **子がある X を中止する理由**: 子の親は不変なので、X に削除の印を付けると、子は N ではなく P の親につながってしまう。親を付け替える仕組みは持たない(D-15)。
- **現在位置が P を中止する理由**: P に削除の印を付けると HEAD が削除済みの版を指す。移動すると作業ファイルが変わるので、利用者に goto させる。
- **書き込み順と中断**: N → コメント → HEAD → 削除印 → oplog。どこで止まっても、「X と同じ内容の N が増えた」「P・X の片方だけに削除の印が付いた」のいずれかで、記録済みのデータは失われず、HEAD は有効な版を指す(N を作る前の HEAD は X、後は N)。
- **名前変更の記録**(`_compose_renames`): 表示用。P の記録(祖父母→P)と X の記録(P→X)をつなぎ、`a→b→c` は `a→c`(類似度は小さい方)。X の tree に無い名前、元に戻った名前、祖父母の tree に無い名前からの記録は除く(祖父母が根の前なら記録なし)。
- **stats**: `new_bytes` は P と X の合計、`total_bytes` は X のもの。

### 4.14 restore(指定ファイルの復元)

指定のファイルだけを版 S の内容に戻す(仕様書 3.15節、D-23)。復元の仕組みは移動系(4.1節・4.6節)をそのまま使い、移動先の tree の代わりに「作業フォルダの現状に、指定のファイルだけ S の内容を重ねた tree」を渡す。HEAD は自動コミット以外では変えない。

```
lock → recover → S = resolve(rev)(自動コミットの前の HEAD で解決)
→ 事前検査(何も変えない):
     S が tree_known でない → BrokenVersion
     パスの対応付け(_match_paths。候補は S・HEAD の tree と走査した追跡ファイル)。無ければ UsageError
     check_target({p: S.tree[p] | p ∈ 指定 ∩ S})  パス・マニフェスト・追跡対象外との衝突
→ state = worktree.state(base=HEAD.tree, store_chunks=True, no_cache=指定)
→ target = state.tree に、指定の p を S.tree[p] で上書き(S に無ければ除く)
→ 上書き・削除する p の現在の内容が、どの有効な版の tree にも無ければ:
     指定外の欠落があり allow_missing でない → MissingFiles
     auto = new_commit(parent=HEAD, tree=state.tree, kind="auto") → HEAD = auto → bvc.lock → index
→ worktree.restore(target, state, HEAD, on_committed=set_head)
→ (変化があれば)oplog("restore", created=[auto])
```

- **自動コミットの条件**: 移動系と違い、指定外のファイルは触らないので、それらの変更は自動コミットの理由にしない。指定のファイルも、内容が既にいずれかの有効な版にあれば失われないので自動コミットしない。同じファイルを版を変えて何度も戻しても、自動コミットが増えないようにするためである。HEAD の版が壊れている場合は、移動系と同じく必ず自動コミットする。
- **欠落**: 指定のファイルの欠落は、復元で戻すので問題にしない。自動コミットしない場合は、指定外の欠落も記録しないので問題にしない。
- **index**: 復元の完了時に `target` で更新される(`_complete`)。target は作業フォルダの現状と一致するので、指定外のファイルの記録もそのまま正しい。
- **中断**: journal の `head` は HEAD(変わらない、または自動コミット)なので、recover は通常の復元と同じく後始末できる。

## 5. git 連携(gitlink.py)

gitlink は repo から使う下位層で、history・store を知らない(版の検索やデータの検査は repo が行う)。

| 関数・クラス | 内容 |
|---|---|
| `tree_hash(tree)` | tree を正規化 JSON にした SHA-256。版の同一判定と pins に使う |
| `lock_bytes(commit_id, tree, manifests)` | bvc.lock の内容。キーをソートし、インデント付き・末尾に改行(1ファイルの変更が数行の差分になる) |
| `parse_lock(data, what)` / `read_lock(path)` | 解析と検査(format、パスは `check_relpath` で NFC のままであること、sha、size)。不正なら `CorruptData` / `UnsafePath` / `UnsupportedFormat`。`read_lock` は無ければ None |
| `write_lock(workdir, lock_file, data, tmpdir)` | `resolve_in_workdir` を通してから原子的に書く |
| `read_lockstate` / `write_lockstate` | lockstate.json。`(記録があるか, tree_hash)` |
| `Git(workdir)` | subprocess で git を呼ぶ(cwd は作業フォルダ、標準入力は DEVNULL)。失敗は `GitFailed`(終了コード3)。フックから呼ばれたときは、git が設定した環境変数(`GIT_INDEX_FILE` など)をそのまま引き継ぐ |
| `Git.history_blobs(path)` | gc 用。`git log --all --reflog --full-history -m --no-renames --format= --raw --no-abbrev -z -- <path>` で bvc.lock を変えたコミットの差分を読み、変更前後の blob を集める(マージは各親との差分。`--all` には stash も含まれる)。ステージの blob も加える。内容は `git cat-file --batch` でまとめて読む |
| `Git.staged(path)` / `blob_at(rev, path)` | pre-commit / post-commit 用(`ls-files -s`、`ls-tree` → `cat-file`)。パスは作業フォルダからの相対パスのまま渡す |
| `install_hooks(hooks_dir, subdir, command)` | フックのフォルダは `git rev-parse --git-path hooks`(core.hooksPath を反映)。subdir は `Git.workdir_prefix()`(`git rev-parse --show-prefix`。作業ツリーの最上位から作業フォルダへの相対パス。最上位なら空)。無ければ作り、`HOOK_MARK` の行か bvc を呼ぶ行を含むフックは設置済みとし、それ以外は上書きせずに追記すべき行を返す。【互換対応・削除予定 LEGACY-HOOK-C】以前の版が書いた絶対パスの `-C` は、該当部分だけを原子的に置き換える(実行権限は保つ。`HooksResult.updated`) |

**bvc.lock の更新(`Repo._update_lock`)**: HEAD を書いた直後(commit、init、移動系の `on_committed`、移動系の自動コミット。sync の自動コミットを除く)に呼ぶ。

1. 作業ツリーに bvc.lock が無く、lockstate の記録がある → bvc が書いた後で無くなった(bvc.lock の無いコミットへ checkout した)とみなし、作らない。lockstate を `tree_hash: null` にする。作ると git から見て追跡されていない bvc.lock が残り、bvc.lock のあるブランチへの checkout が拒否されるため(仕様書 5.1節)。
2. bvc.lock の内容(tree)が新しい HEAD と同じ → 書き換えない(番号の違う同じ内容の版に移ったときに、git に差分を出さない)。
3. それ以外は書き換える。書き換える前の bvc.lock が lockstate とも一致しなければ(非同期状態)、警告し、元の内容を oplog(`op: lock_overwrite`、`previous`)に記録する。
4. lockstate を新しい tree_hash にする。

書き込みの失敗(OSError など)は警告にとどめ、操作は成功とする。次に開いたときに下の規則で書き直す。

**開いたときの検査(`Repo._check_lock`)**: recover・管理ファイルの復旧の後に行う。現在位置の版・bvc.lock・lockstate の状態は `_lock_view` で1回だけ読み、書き直すときは `_update_lock` にそのまま渡す。

| 作業ツリーの bvc.lock | 判定 |
|---|---|
| 無い(lockstate の記録なし) | まだ書いていない(init の途中で中断など)→ 書く |
| 無い(記録あり) | `missing`(bvc.lock の無いコミット) |
| @ と同じ内容 | `ok`(lockstate が古ければ更新) |
| lockstate と同じ内容で @ と違う | HEAD の更新後、bvc.lock を書く前に中断した → 書き直す |
| それ以外・読めない | `out_of_sync`(非同期状態)。警告する |

lockstate が `null`(bvc.lock が無い状態)のときに bvc.lock が現れた場合は、中断とは区別して非同期状態とする(bvc.lock の無いコミットで版を進めてから、bvc.lock のあるコミットへ戻った場合。post-checkout の sync で合わせる)。lockstate が壊れている場合も `(記録あり, null)` とし、bvc.lock を作らない・黙って書き直さない側に倒す(D-15)。

**sync(M6-4)**: bvc.lock の tree と同じ内容の、有効な健全な版を探す(`bvc_commit` を優先し、無ければ新しい順)。見つからなければ、全マニフェスト・チャンクが揃い、`size`・`sha256` がマニフェストと一致することを確かめてから(1つでも違えば `CorruptData` で何も変えない)、`_move` に `import_tree` を渡す。`_move` は自動コミットの後に、自動コミット(無ければ現在位置)の子として kind=import の版を作り、そこへ移動する。

**pre-commit**: snapshot なら `commit(kind="auto", message="auto: git pre-commit")` を行い、bvc.lock がステージに載っていれば `git add` する(bvc.lock を外したコミットには加えない)。reject なら未コミットの変更で `SafetyAbort`。ステージされた bvc.lock は、内容が同じ健全な版(削除済みを含む)があり、`size`・`sha256` がマニフェストと一致することを確かめる。満たさなければ `SafetyAbort`(git commit が中止される)。

**post-commit(`git pin`)**: git の HEAD の bvc.lock と内容が同じ健全な版(削除済みを含む)を pins に記録する。同じ組が記録済みなら何もしない。

**post-checkout**: bvc.lock が無ければ何もしない。@ と内容が違う(または読めない)ときだけ sync する。失敗時は cli が目立つ警告を出し、エラーの終了コードを返す(git checkout の終了コードになる)。

**gc(M6-5)**: git 連携が有効なら、作業ツリーの bvc.lock と(`--no-git` でなければ)`history_blobs` の全 bvc.lock が参照するマニフェストを mark に加える。git の失敗は `GitFailed`、読めない bvc.lock は `SafetyAbort` で、何も消さない。すでに存在しないマニフェストは加えない(読めないマニフェストとして扱うと、チャンクの削除まで止まるため)。

フック(`.git/hooks/pre-commit` など)の中身は、`sh` から Python を呼ぶだけにする。Git for Windows でも動く。

```sh
#!/bin/sh
# bvc: bvc git install-hooks が設置したフック
exec python -m bvc git pre-commit
```

git はフックの作業ディレクトリを作業ツリーの最上位にするので、作業フォルダが最上位なら `-C` は書かない。最上位の下にあるときだけ、最上位からの相対パスを `-C "<相対パス>"` として書く。作業フォルダの絶対パスを書くと、フォルダの移動・複製で壊れる(または複製が元のフォルダを操作する)ため(N-50)。

zipapp から実行している場合はその pyz のパスを書く(`python "<bvc.pyz のパス>"`)。そうでない場合(開発時の `pip install -e` など)は `python -m bvc` を書く。Python は PATH 上の `python` とし、別の Python を使う環境では利用者がフックを書き換える。パスは `/` 区切りにし、sh のダブルクォートで囲む(`\`、`"`、`$`、バッククォートは `\` でエスケープする)。

## 7. テスト方針

テスト観点の一覧は「04_テスト観点.md」にまとめる。実装の方針は次の通り。

- **テスト基盤**: 単体テストは `unittest` でも実行できる形で書き、結合テストは pytest 形式でよい(AGENTS.md)。実行は `python -m pytest`。各テストで一時フォルダに作業フォルダを作り、終了時に削除する。
- **時間のかかるテスト**: `slow` とし、既定では skip する。`--run-slow` を付けたとき、またはテストを個別に指定したとき(GUI で1件を選んだときなど)だけ実行する。本体の待機(書き込み中の再試行)は差し替えず、実際に待つ。
- **障害注入**: fsutil にモジュール変数 `_fault_hook: Callable[[str], None] | None`(既定は None)を置く。原子的書き込み、`os.replace`、チャンクの書き込みの前に段階名(例: `atomic_write:HEAD.json`、`replace:swap:3`)を渡して呼ぶ。テストからは `unittest.mock.patch` で、指定の段階・回数で例外を送出する関数を差し込む。
- **強制終了**: テスト用のドライバスクリプトを subprocess で起動する。ドライバは `Repo` を import して操作し、進捗コールバックと `_fault_hook` で段階名を標準出力に書く。親は指定の段階名を読んだら kill し、その後 recover と verify で整合性を確認する。本体にはテスト専用の分岐(環境変数など)を入れない。
- **Python のバージョン**: 3.11 で使えない機能(`shutil.rmtree` の `onexc`、`itertools.batched`、`type` 文など)を使わない。
- **長いパス**: `fsutil.LONG_PATH_THRESHOLD` を 0 に差し替えて全テストを流す設定を用意し(pytest のオプション `--force-long-path`)、`\\?\` 付きの道筋を常に確認できるようにする。Windows では既定の実行に加えてこの設定でも流す。
- **破損の再現**: チャンクファイルの削除、1バイト反転、切り詰め、codec ID の書き換え。版・マニフェストの JSON の破壊や改ざん。
- **大容量**: スパースファイルや、疑似乱数で生成したファイルを使う。tracemalloc でメモリ使用量を確認する。
