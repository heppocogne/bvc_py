## 1. 基本的な使い方

```
cd 作業フォルダ
bvc init --track "*.bin" --track "mesh/**/*.dat"
(アプリで作業)
bvc commit -m "メッシュを細分化"
bvc undo              ← 1つ前の版に戻る
bvc redo              ← 戻したのを取り消す
bvc log
```

## 2. 共通仕様

### 2.1 呼び出し

```
bvc [共通オプション] <コマンド> [引数]
```

| 共通オプション | 意味 |
|---|---|
| `-C <パス>` | 作業フォルダを指定する(省略時はカレントから上位へ `.bvc` を探す) |
| `--json` | 結果を JSON で出力する(GUI・スクリプト向け) |
| `-q` | 通常の出力を抑制する |

共通オプションはコマンド名の前に書く(`bvc --json log`)。出力の形式は 2.11節。

配布版は1ファイルの `bvc.pyz`(Python 3.11 以降で `python bvc.pyz <コマンド>` として実行する)で、Windows 向けに同じフォルダに置く `bvc.cmd` を添える。`bvc.cmd` のあるフォルダを PATH に加えると `bvc <コマンド>` で実行でき、終了コードもそのまま返る。

### 2.2 終了コード

| コード | 意味 |
|---|---|
| 0 | 成功、または要求された状態がすでに成立している(変更なしの commit、現在位置への goto、同期済みでの sync、bvc.lock の無いコミットでの sync(`--require-lock` なし)、削除対象の無い gc。メッセージで「変更なし」等と表示する) |
| 1 | エラー(データ不整合、見つからない等) |
| 2 | 引数の誤り |
| 3 | 安全のため中止(ファイルの欠落、使用中・書き込み中、ロック中) |
| 4 | 要求された移動ができない(根での undo、現在位置が根のときの discard、先端での redo、進む先が複数ある redo)。データは何も変わっていない |

判断基準は「コマンドの後で、利用者が期待した状態になっているか」である。`bvc undo && 解析実行` のようなスクリプトで、意図しない版のまま後続の処理が走らないようにするため、移動できなかった場合は 0 以外を返す。
`--json` の出力には、状態を実際に変えたかどうかを表す `"changed": true/false` を必ず含める。エラーで終わった場合も JSON を出力し、`exit_code` に終了コードを入れる(2.11節)。

### 2.3 版の指定(リビジョン式)

| 書き方 | 意味 |
|---|---|
| `N` | 版番号(`0` は init 時点) |
| `@` | 現在位置 |
| `<式>-` | その親(discard 済みは飛ばす)。`@--` のように連結可 |
| `<式>+` | その子のうち、現在のブランチの先端へ向かう側 |
| `<名前>` | その名前のブランチの先端 |

ブランチ名の制約は次の通り。数字だけの名前、`@` で始まる名前、`+` `-` を含む名前、空白を含む名前は使えない。大文字小文字は区別する。

### 2.4 追跡パターン

- 作業フォルダからの相対パスに対する glob で、区切り文字は `/`。
- `*` と `?` は `/` を越えない。`**` は0階層以上のフォルダに一致する。
- Windows では大文字小文字を区別せずに照合する。
- `track` に一致し、かつ `ignore` に一致しないファイルが追跡対象になる。`.bvc/` 配下は常に対象外。
- 大文字小文字だけが異なる2つのパスが追跡対象になった場合はエラーとする。

### 2.5 変更の検出

- 追跡ファイルのサイズと更新日時が前回の記録と同じなら、「未変更」とみなす。
- 異なる場合は中身をハッシュして判定する。内容が同じなら未変更として扱い、記録だけ更新する。
- 読み取りの前後でサイズまたは更新日時が変わった場合は「書き込み中」と判断し、1秒おきに最大3回再試行する。それでも変わる場合は中止する(終了コード3)。
- ファイルを開けない場合(他のアプリが排他で使用中など)は中止する(終了コード3)。

### 2.6 欠落と名前変更の判定

前の版(現在位置)と作業フォルダを比べ、次の順に判定する。

1. **名前変更(完全一致)**: 消えたファイルと新しいファイルの SHA-256 が一致するもの。分割方式が異なっていても、内容が同じなら一致とみなす。同じ内容のファイルが複数あれば、パスの辞書順で1対1に対応付ける。
2. **名前変更(類似)**: 残ったもの同士で共通チャンクの割合(新ファイル基準のバイト比)を計算し、`rename_threshold`(既定0.5)以上の組を、割合の高い順に採用する。割合が同じならパスの辞書順とする(実行ごとに結果が変わらない)。
3. **手動指定**: `--rename 旧=新` で指定された組は、上記より優先する。
4. **欠落(missing)**: 対応先の無い、消えたファイル。

`--rename` のパスは作業フォルダからの相対パスで、`\` も区切りとして受け付ける。大文字小文字だけが異なる指定は、対応先が一意に決まれば受け付ける。次の場合は何も記録せずに引数の誤り(終了コード2)とする。

- 旧が「前の版にあり、作業フォルダから消えた追跡ファイル」でない
- 新が「新しく追加された追跡ファイル」でない
- 同じパスを複数の組で指定した、または使えないパス(2.9節)を指定した

この判定は、log の先頭に表示する未コミットの変更と自動コミット(2.7節)でも同じ結果になる。

欠落が1つでもあれば中止する(終了コード3)。`--allow-missing` を付けた場合は、削除として記録する。
中止する際、追跡パターン外に同じ内容のファイルがあれば、ヒントとして表示する。探すのは作業フォルダ直下と、消えたファイルのあったフォルダだけで、`--allow-missing` のときは探さない。`--json` では `details.hints`(消えたパス → 候補のパスのリスト)に入る。

```
中止: 追跡ファイルが見つかりません
  missing: result.bin
  ヒント: パターン外に同じ内容のファイルがあります: result.bin.tmp
  削除として記録するには --allow-missing を指定してください
```

### 2.7 自動コミット

現在位置を動かすコマンド(undo, redo, goto, discard, sync)は、実行前に未コミットの変更の有無を確認する。変更があれば、次の内容で版を作成してから本来の処理を行う。

- 種別(kind): `auto`
- メッセージ: `auto: before <コマンド> <引数>`(例: `auto: before goto 5`、`auto: before undo`)
- 作成規則は commit と同じ(ブランチ規則、欠落の判定を含む)

欠落がある場合は commit と同様に中止する。各コマンドに `--allow-missing` を付けると、そのまま自動コミットに引き継ぐ。

### 2.8 作業ファイルの復元

移動先の版の状態に、作業フォルダの追跡ファイルを**完全に一致**させる。

- 移動先の版にあるファイルは書き出す(内容が同じものは触らない)。
- 移動先の版に無い追跡ファイルは削除する。削除前の内容は自動コミットで保存済み。
- 追跡対象外のファイルには一切触れない。
- **上書き・削除の前の確認**: 上書きまたは削除する作業ファイルは、stat キャッシュを使わずに必ず中身をハッシュし、その内容が保存済み(現在位置の版か自動コミット)であることを確認する。更新日時を保ったまま中身が変わっていた場合も、ここで検出して自動コミットに含める。移動元と移動先で内容が同じファイルには触れないので、この確認も不要。
- **追跡対象外との衝突**: 書き出す先に追跡対象外のファイルやフォルダがある場合は、何もせずに中止する(終了コード3)。設定を変えて追跡から外したファイルなど、保存されていないファイルを上書きしないためである。
- 全部成功か全部元通りのどちらかにする。1つでも置き換えに失敗した場合(使用中など)は、全ファイルを元に戻し、現在位置も変えずに中止する(終了コード3)。
- 強制終了後に次のコマンドを実行したときは、中断していた復元を自動で後始末(元に戻すか、完了させる)してから本来の処理に入る。
- 復元前に空き容量を確認し、足りなければ何もせずに中止する(終了コード3)。
- 復元したファイルの更新日時は、復元した時刻とする(要件定義書 T-10 で再検討)。

### 2.9 データが壊れている場合の動作

**「壊れた版」の定義**: 版ファイル自体が読めない、または復元に必要なマニフェストかチャンクが、1つでも欠損・破損している版。

**検出の契機**: 復元時、verify 時、コミット時の既存チャンク検査で、ハッシュの不一致、読み込みエラー、形式エラーが見つかったとき。

**検出したときの処理**

- 壊れたチャンクやマニフェストは `.bvc/quarantine/` へ移し(隔離)、以後は存在しないものとして扱う。
- 検出結果は健全性の記録(health)に残し、log では該当する版に `✗` を付ける。log 自体はデータを検査しないので、まだ検出されていない破損には `✗` が付かない(verify で検出する)。

**各操作での扱い**

| 操作 | 動作 |
|---|---|
| commit | 隔離済み・欠損のチャンクは、作業ファイルから新たに保存し直す。新しい版は、壊れたデータを参照しない |
| undo / redo | 移動先が壊れた版なら、作業ファイルを変えずに中止する(終了コード1。自動コミットも作らない)。`--skip-broken` を付けると、同じ方向で最も近い健全な版まで進む。その方向に健全な版が無ければ、何も変えずに中止する(終了コード1) |
| goto | 壊れた版を指定したら中止する。健全な版なら、途中の版の状態に関係なく移動できる(各版が全体のスナップショットのため) |
| discard, note, branch | 壊れた版にも実行できる。ただし、版ファイル自体が読めない版は属するブランチが分からないので、`branch name` の対象にはできない(エラー) |
| log | 版ファイルが読めない版は `✗ (読み込み不可)` と表示する。その子は、記録済みの祖先情報でつなぐ |
| verify --repair | 壊れたチャンクを、現在の作業ファイルに同じ内容があれば修復する |

**管理ファイルが壊れた場合の自動復旧**

| ファイル | 復旧方法 |
|---|---|
| index.json | 捨てて作り直す(全追跡ファイルを再ハッシュ) |
| counters.json | 版・削除印・操作ログの最大番号から再計算する |
| HEAD.json | 操作ログの最後の `after` を使う。それも無ければ、作業ファイルと内容が一致する版を探す。見つからなければ最新の版にして、警告を表示する(作業ファイルは変えない)。存在しない版・削除済みの版を指している場合も復旧の対象とする |
| branches.json | 名前を失って空で作り直し、警告を表示する |
| config.json | 自動復旧しない。エラーで中止し、修正方法を案内する |
| JSONL 系 | 壊れた行を読み飛ばし、警告を表示する |
| health.json | 空で作り直し、警告を表示する(壊れたデータは次の verify で再検出される) |

- 自動復旧するのは、ファイルが無い・解析できない・形式が不正な場合だけで、作業ファイルは変えない。復旧したら警告を表示し、操作ログに記録する(`op: "recover_control"`)。
- 読み込み自体に失敗した場合(他のアプリが使用中など)は、何も変えずに中止する(終了コード3)。知らない format の場合も、何も変えずに中止する(終了コード1)。

### 2.10 パスの扱い

- 版(tree と名前変更の記録)・マニフェスト・bvc.lock に記録されたパスは、使う前に必ず検査する。次のいずれかに当たるものは不正データとして扱い、そのパスを含む版は「壊れた版」とみなす。
  - 絶対パス、ドライブ指定(`C:`)、UNC(`\\`)
  - `..` や `.` の要素、空の要素、`\` を含むもの
  - 先頭の要素が `.bvc`(大文字小文字を問わない)
  - Unicode の NFC に正規化すると変わるもの(bvc は NFC で記録するため)
  - Windows の予約名(`CON`, `NUL`, `COM1`, `CONIN$` など)、末尾がドットまたは空白の要素、使用できない文字(`<>:"|?*` と制御文字)
- 書き込み・削除の直前には、実際の絶対パスが作業フォルダの内側にあり、途中にシンボリックリンクやジャンクションを含まないことを確認する。
- Windows の 8.3 形式の短い名前(`BVC~1` など)は、名前の検査を通っても `.bvc` と同じ実体を指すことがある。書き込み・削除の直前に実際の場所を確かめ、`.bvc` の中を指していれば何も変えずに中止する(終了コード1)。
- 作業フォルダ内のシンボリックリンク・ジャンクションは、たどらずに追跡対象外とする。パターンに一致した場合は警告を表示する。
- 版番号とハッシュ値(16進64桁)も、形式を検査してからファイル名に使う。
- パスは作業フォルダからの相対パスで保持する。作業フォルダごと移動・改名しても、そのまま使える。
- パスは Unicode の NFC に正規化して保存する。
- 作業フォルダの外の場所を設定で指定する場合(将来の mirror など)は、絶対パスで書く(ドライブ指定・UNC のどちらも可)。作業フォルダや `.bvc` の内側を指す値は受け付けない。
- Windows で 260 文字を超えるパスも扱える(OS の長いパスの設定が無効でもよい)。作業フォルダ自体のパスが長い場合も同様。
- 作業フォルダはネットワークフォルダ(UNC、ネットワークドライブ)に置いても動作する。ただし、ネットワーク上では強制終了・電源断への耐性がローカルディスクより下がるため、推奨はローカルディスクとする。
  - ネットワークドライブ・subst のドライブ上の作業フォルダは、実際の場所(`realpath` の結果。ネットワークドライブなら UNC)として扱い、表示やエラーメッセージもそのパスになる。
  - 確認済みの構成(M4-12): ローカルの管理共有(`\\localhost\C$\…`)、`net use` で割り当てたネットワークドライブ、subst のドライブ。いずれも基本操作(init, commit, undo, redo, goto, status, verify, discard, gc、サブフォルダからの実行)が、誤って中止することなく動いた。実際のファイルサーバー・NAS での確認は M5 の実機確認で行う。

### 2.11 出力

**通常の出力**

- コマンドの結果(log の表示、branch の一覧、`--version`)とお知らせ(「版 8 を作成しました」など)は標準出力に書く。
- 警告・エラーは標準エラーに書く。先頭に「警告: 」「エラー: 」、安全のための中止(終了コード3)なら「中止: 」を付ける。
- `-q` を付けると、お知らせを出さない(結果の表示、警告・エラーは出す)。

**進捗の表示**

- 時間のかかる処理(init, commit, undo, redo, goto, discard, gc, verify, sync)は、標準エラーが端末のときだけ、1行を上書きして進捗を表示する。例: `保存 model.bin: 512.0 MiB / 1.0 GiB (50%)`。
- 段階は、保存(ファイルの取り込み)・展開(復元するファイルの書き出し)・置き換え・チャンクの検査・マニフェストの検査・修復・削除。量は、保存と展開がバイト数、それ以外は件数。
- 表示の更新は 0.1 秒に1回まで(段階やファイルが変わったときはすぐ更新する)。お知らせ・警告を書く前と、コマンドの終わりに進捗の行を消す。
- 標準エラーが端末でない場合(リダイレクト・パイプ)、`-q`、`--json` では表示しない。

**`--json`**

- 標準出力に、JSON のオブジェクトを1つだけ書く。お知らせ・警告・進捗は標準エラーにも出さない。
- すべての出力に、次の2つを含める。
  - `changed`: 状態を実際に変えたか(2.2節)
  - `warnings`: 警告のメッセージ(文字列)の配列。警告が無ければ空の配列
- 成功した場合は、コマンドの結果を加える。repo 層の結果(dataclass。設計書 3.1節)のフィールドと公開のプロパティ(`WorkState.dirty`、`VerifyReport.ok`)をそのままキーにする。組(名前変更の `[旧, 新, 類似度]` など)は配列、辞書のキーは文字列になる。

| コマンド | `changed` と `warnings` 以外のキー |
|---|---|
| init | `workdir`(作業フォルダの絶対パス)、`commit`(版 0)、`hooks`(`--git` のときフックの設置結果。git install-hooks と同じ形。それ以外は null) |
| commit | `commit`(変更なしなら null)、`state`(作業フォルダの状態)、`new_branch` |
| log | `uncommitted`(未コミットの変更。確認できなければ null)、`entries`(新しい順の版)、`lock_status`(`ok` / `out_of_sync` / `missing` / `disabled`。3.11節) |
| undo / redo / goto | `before`、`after`(`{"at": 版, "branch": ブランチ番号}`)、`auto_commit`、`restored`、`deleted`、`skipped` |
| sync | undo / redo / goto の項目、`lock_found`、`imported` |
| git install-hooks | `installed`(設置したフック)、`already`(設置済み)、`manual`(追記が必要なフック → 追記すべき行) |
| git pin | `pin`(`git`、`bvc`、`tree_hash`。記録しなければ null) |
| git pre-commit | `auto_commit`(snapshot で作った版。無ければ null)、`staged_ok`(ステージされた bvc.lock を検査したか) |
| git post-checkout | `synced`(sync を実行したか)、`sync`(sync の結果。実行しなければ null) |
| note | `note`(`commit_id`、`time`、`text`) |
| branch | 一覧は `branches`、name / unname は `branch`(`number`、`name`、`tip`、`fork`、`is_current`) |
| discard | `discarded`、`before`、`after`、`auto_commit`、`restored`、`deleted` |
| gc | `dry_run`、`deleted_commits`、`deleted_manifests`、`deleted_chunks`、`deleted_tmp`、`freed_bytes`、`skipped` |
| verify | `ok` と 3.10節の項目、`quick`、`repair`、`checked_*` |
| `--version` | `version` |

- エラーで終わった場合は、次の形にする(引数の誤りも同じ。`type` は `UsageError`)。

```json
{
  "changed": false,
  "error": "追跡ファイルが見つかりません …",
  "type": "MissingFiles",
  "exit_code": 3,
  "details": {"missing": ["a.bin"], "hints": {}},
  "warnings": []
}
```

- `type` はエラーの種類(設計書 3.7節の例外クラス名)。`details` は種類ごとの付加情報(欠落したパス、移動先の候補 `candidates` など)。

**文字コード**

- 出力先の文字コード(リダイレクト・パイプでは Windows の既定で cp932)で表せない記号は、表せるものに置き換える(`✗` → `×`、`╯` → `┘` など。それも表せなければ ASCII の `x` `/` など)。ファイル名など、それ以外の表せない文字は `?` にする。
- `--json` は、出力先の文字コードが UTF-8 でなければ、ASCII 以外の文字を `\uXXXX` で書く(どの文字コードで受け取っても、JSON として正しく読める)。

## 3. コマンド仕様

### 3.1 init

```
bvc init --track <パターン> [<パターン> ...] [--track ...] [--ignore <パターン> [<パターン> ...] ...]
         [--chunker fixed|gear|whole] [--chunk-size <サイズ>] [--compression auto|none|zlib]
         [--git]
```

- `.bvc/` を作成し、設定を保存する。作業フォルダは共通オプション `-C` で指定する(init に位置引数は無い)。
- その時点で追跡対象のファイルを版 `0`(kind=`init`)として記録する。対象が0件でも作成する(警告を表示)。
- `--track`・`--ignore` は、1つのオプションに複数のパターンを続けて書ける(`--track "*.exe" "*.dll"`)。オプションを繰り返す書き方(`--track "*.exe" --track "*.dll"`)と混在してもよい。
- `--git` を指定すると、git 連携を有効にし、`bvc.lock` を作成する。あわせて git のフックを設置する(3.12節の install-hooks と同じ。既存のフックがあれば、追記すべき行を表示する)。推奨する .gitignore(5.2節)も表示する。
  - 作業フォルダが git の作業ツリーの中に無い場合は、エラー(終了コード1)で終わり、`.bvc/` も作らない。先に `git init` を実行する。
  - フックの設置に失敗しても init は成功とし、警告を表示する(後から `bvc git install-hooks` で設置できる)。
- すでに `.bvc/` がある場合はエラー(終了コード1)。
- サイズの指定は `4M` や `1048576` のように書ける。
- `--chunker gear` の場合、分割に使う seed を init が乱数で決めて設定に保存する。自分で決めたい場合は、init 後に config.json の `chunker.seed` を編集する。config.json を手で編集して gear に切り替えるときは、seed も書く必要がある(無ければエラーで中止する)。

追跡パターンを後から変えるときは、`.bvc/config.json` を直接編集する。

### 3.2 commit

```
bvc commit [-m <メッセージ>] [--allow-missing] [--rename 旧=新 ...]
```

- 追跡ファイルの現状を新しい版として記録する。
- **ブランチ規則**: 現在位置に子(discard されていない版)がある場合は、新しいブランチを作成する。子が無い場合は、現在位置の版と同じブランチに追加する。
- 変更が無い場合は何もせず、「変更なし」と表示して正常終了する(終了コード0、`changed: false`)。版へのコメントには note を使う。
- 記録後、現在位置を新しい版にする。

出力例:
```
版 8 を作成しました(新しいブランチを作成)
  modified: model.bin   (新規データ 52.0 MiB / 1.0 GiB)
  renamed:  a.bin → b.bin (87%)
```

類似度(%)は類似による名前変更にだけ付ける(切り捨て)。完全一致と手動指定には付けない。

### 3.3 log

```
bvc log [--discarded] [-n <件数>]
```

- 版のツリーを新しい順に表示する。
- 各版について、番号、ブランチ名(名前付きブランチの先端のみ)、日時、種別、メッセージ、note を表示する。
- 先頭には、未コミットの変更(modified/added/renamed/missing)を表示する。
- `--discarded` を付けると、削除済み(gc 前)の版も表示する。
- git 連携が有効で非同期状態(3.11節)のときは、先頭に警告を表示する。

出力例:
```
未コミットの変更: model.bin (modified)
@  8  [細分化]  09-25 20:10  メッシュを細分化
│     note: 収束せず、要再検討
○  7            09-25 19:55  auto: before undo
│ ○  6          09-25 19:40  荷重条件を変更
├─╯
○  3            09-25 18:00  初期メッシュ
○  0            09-25 17:00  (init)
```

### 3.4 undo / redo

```
bvc undo [-m <理由>] [--allow-missing] [--skip-broken]
bvc redo [-m <理由>] [--allow-missing] [--skip-broken]
```

- undo: 現在位置を親の版に移動し、作業ファイルを復元する。現在のブランチ(redo で進む方向)は変えない。
- redo: 現在のブランチの先端に向かって子の版へ移動する。現在位置が現在のブランチの経路上に無い場合で、子が1つだけならその子へ進む。複数ある場合は候補を表示してエラーにする(終了コード4)。
- 根(親なし)での undo、先端での redo は終了コード4。移動できない場合は、未コミットの変更があっても自動コミットを作らない。
- 未コミットの変更を自動コミットして undo した場合、現在のブランチは自動コミットのブランチになる。redo を繰り返すと、編集内容(自動コミット)に戻れる。
- `-m` の理由は操作ログに記録する。
- 移動先が壊れた版の場合は中止する(終了コード1)。`--skip-broken` を付けると、壊れた版を飛ばして、同じ方向で最も近い健全な版へ移動し、飛ばした版を表示する(2.9節)。
- 壊れた版の判定には、版ファイル・パス・マニフェスト・チャンクの有無とヘッダを使う。チャンクの中身の照合は復元時に行い、そこで破損が見つかった場合は、作業ファイルを変えずに中止する(以後は、隔離の記録により飛ばせる)。

### 3.5 goto

```
bvc goto <版> [--allow-missing]
```

- 指定した版へ移動し、作業ファイルを復元する。
- ブランチ名で指定した場合は、そのブランチを現在のブランチにする。版番号で指定した場合は、その版が属するブランチを現在のブランチにする。
- 壊れた版は指定できない(中止する)。途中の版が壊れていても、健全な版へは直接移動できる。
- 現在位置(`@` や現在の版番号)を指定した場合は何もしない(終了コード0、`changed: false`。未コミットの変更もそのまま)。ブランチ名で指定し、位置は同じでブランチだけが異なる場合は、現在のブランチだけを切り替える。

### 3.6 note

```
bvc note -m <本文> [-r <版>]
```

- 版にコメントを追記する(`-r` 省略時は `@`)。追記のみで、編集・削除はできない。
- 本文と版をオプションで明示するので、`bvc note -m 2` のように本文が数字でも、版番号と取り違えない。
- 実行後に、対象の版の番号とメッセージを表示する(例: `版 7(メッシュを細分化)にコメントを追加しました`)。メッセージが空なら種別(`init`, `auto` など)、版ファイルが読めなければ「読み込み不可」と表示する。
- 自動コミットにも付けられる。削除済みの版には付けられない(版番号で指定できないため)。
- 本文の省略・空の本文は引数の誤り(終了コード2)。
- コメントは、その版が gc で消えるときに一緒に消える。

### 3.7 branch

```
bvc branch                        ブランチ一覧
bvc branch name <名前> [<版>]     <版>が属するブランチに名前を付ける(省略時は @)。既存の名前は付け替える
bvc branch unname <名前>          名前を外す
```

一覧には、名前(無ければ「(名前なし)」)、先端の版番号、分岐元の版番号、現在のブランチかどうかを表示する。内部のブランチ番号は表示しない(`--json` では識別用に出力する)。

```
* 細分化      先端 8  分岐元 3
  (名前なし)  先端 6  分岐元 3
  (名前なし)  先端 2  分岐元 なし
```

- `*` が現在のブランチ。分岐元は、そのブランチの最初の版の親(つなぎ直し後)。根から始まるブランチは「なし」。
- 一覧に出すのは、有効な版のあるブランチ、名前の付いたブランチ、現在のブランチ。名前の付いたブランチの版がすべて削除済みになった場合も、名前を外せるように一覧に残す(先端は「なし」)。
- 1つのブランチに付く名前は1つ。名前の付いたブランチに別の名前を付けると、古い名前は外れる。
- 名前の制約(2.3節)に反する名前は引数の誤り(終了コード2)。無い名前の unname はエラー(終了コード1)。

**追従の仕方(git 型)**: ブランチの先端で commit すると、ブランチは自動で伸び、名前もそれに付いていく。途中の版から commit した場合は、新しいブランチができる(名前は付かない)。名前の付いたブランチは元の枝に残る。
版は名前の有無に関係なく gc で消えないので、名前を付け忘れてもデータは失われない。

### 3.8 discard

```
bvc discard [<版>] [--force] [--allow-missing]
```

- 指定の版に削除の印を付ける(省略時は `@`)。データは gc まで残る。
- 子の版は、削除した版の親(さらに削除済みならその先)につなぎ直す。
- 指定の版が現在位置の場合は、親へ移動して作業ファイルを復元する。親が無い場合は、何もせずに終了コード4で終わる(根での undo と同じ。自動コミットも作らない)。
- 未コミットの変更がある場合は、先に自動コミットを作成する。この自動コミットは削除される版の子になり、つなぎ直しの対象になる(作業内容は残る)。移動後の現在のブランチは自動コミットのブランチになり、redo で作業内容に戻れる。
- 削除の印は、移動(復元)が成功してから付ける。復元が失敗した場合は印を付けずに中止する(現在位置は自動コミットのまま。2.8節)。
- git のコミットが参照している版は警告して中止する(終了コード3)。`--force` で実行できる。

出力例:
```
版 8 に削除の印を付けました
  版 7 に移動しました
  未コミットの変更を版 9 に自動コミットしました(auto: before discard)
  restored: model.bin
```

### 3.9 gc

```
bvc gc [--dry-run] [--no-git]
```

- 削除済みの版(git 参照の無いもの)、どの版からも参照されないマニフェストとチャンク、一時ファイルを削除する。
- git 連携が有効な場合は、git の全履歴(全ブランチ・タグ・stash・reflog を含む)にある `bvc.lock` を必ず調べ、参照されているデータを保護する。git の呼び出しに失敗した場合は、何も削除せずに中止する。`--no-git` は、この確認を明示的に省くときだけ使う。
- 作業ツリーの `bvc.lock` が参照するデータも保護する(`--no-git` でも)。作業ツリーや git の履歴に読めない `bvc.lock` があると、参照されるデータが分からないため、何も削除せずに中止する(終了コード3)。作業ツリーの `bvc.lock` が壊れている場合は、`git checkout -- bvc.lock` などで直してから gc する。
- `--dry-run` では削除対象と容量を表示するだけで、何も削除しない。
- gc 後は discard を取り消せない。
- 削除対象が無い場合は「削除対象がありません」と表示する(終了コード0、`changed: false`)。
- 有効な版のうち、版ファイルが読めない(または不正な記録を含む)版があると、その版がどのデータを使っているか分からない。この場合は削除済みの版だけを消し、マニフェストとチャンクは消さない(警告を表示する)。有効な版が使うマニフェストが読めない場合も、チャンクは消さない。その版を discard すれば、次の gc で消せる。
- 途中で中断しても、有効な版はすべて復元できる。もう一度 gc を実行すれば完了する。

出力例:
```
削除対象: 版 5, 6、マニフェスト 3、チャンク 40、一時ファイル 0(合計 160.2 MiB)
```

### 3.10 verify

```
bvc verify [--quick] [--repair]
```

- 全チャンクを読み、ハッシュを照合する。マニフェストと版の参照漏れも検査する。
- `--quick` では、チャンクファイルの存在確認とヘッダの検査だけを行う(圧縮なしのチャンクは長さも確認する)。
- 見つかった異常データは隔離し、健全性の記録を更新する。
- 検査の対象は、有効な版と pin された版。削除済みの版だけが使うデータの異常は、結果に含めない(gc で消える)。
- `--repair` を付けると、隔離・欠損したチャンクとマニフェストを、作業フォルダのファイルを分割した結果から探して、保存し直す。材料にするのは、追跡ファイルすべてと、パターン外で「壊れた版に記録されたファイル名」または「そのファイルのサイズ」が一致するファイル(フォルダは問わない)。分割方式は、設定のもの(rules を含む)と、読めたマニフェストに記録されたものを試す。修復できた版は健全に戻る。
- 異常が残っていれば、壊れた版の一覧を表示し、終了コード1で終わる。`--json` では `ok`・`broken_commits`・`bad_chunks`・`bad_manifests`・`repaired_chunks`・`repaired_manifests` を出力する。

### 3.11 sync(git 連携)

```
bvc sync [--allow-missing] [--require-lock]
```

- `bvc.lock` の内容と作業ファイルを一致させる。基準にするのは、`files` の内容(マニフェストのハッシュ)である。`bvc_commit` の番号は参考情報として扱う。
- 内容が同じ健全な版があれば、そこへ goto する。`bvc_commit` の番号の版と内容が異なる場合は、警告を表示する(別のリポジトリで作られた bvc.lock など)。
- 無い場合でも、必要なデータがすべてリポジトリに残っていれば、種別 `import` の版を作成して移動する。
- データが1つでも欠けている、壊れている、パスが不正、形式が未知のいずれかの場合は、何も変えずに中止する(一部のファイルだけを復元することはしない)。
- 未コミットの変更は、移動系コマンドと同じく、移動の前に自動コミット(`auto: before sync`)で保存する。import の版は、自動コミット(無ければ現在位置)の子として作る。
- `bvc.lock` の内容がすでに現在位置の版と同じなら、何もしない(終了コード0、`changed: false`)。未コミットの変更もそのまま残す。
- sync に失敗すると、git の作業ツリー(コード)とバイナリが食い違ったままになる。これを「非同期状態」として記録し、解消するまで log の先頭と各コマンドの実行時に警告を表示する。
- 作業フォルダに `bvc.lock` が無い場合(bvc.lock をまだ作っていない、または削除したコミットへ git checkout した場合)は、何も変えない。追跡ファイルもそのまま残す。警告を表示して終了コード0(`changed: false`)で終わる。`--require-lock` を付けると、この場合を終了コード1にする(スクリプトで後続の処理を止めたいとき)。
- `--json` では、移動系コマンドの項目に加えて、`lock_found`(bvc.lock があったか)と `imported`(作成した import の版。無ければ null)を出力する。

### 3.12 git サブコマンド

```
bvc git install-hooks     pre-commit / post-commit / post-checkout を設置
bvc git pin               (フック用。post-commit)git の HEAD と bvc の版の対応を記録
bvc git pre-commit        (フック用)
bvc git post-checkout <前の HEAD> <新しい HEAD> <フラグ>   (フック用)
```

- install-hooks は、フックのファイルが無ければ作成する。bvc が設置したフックがすでにあれば何もしない。別の内容のフックがある場合は上書きせず、「下記の処理を追加して下さい」として追記すべき行を表示する。
- フックは `python` で bvc を起動する(PATH 上の python。5.3節)。別の Python を使う環境では、利用者がフックを書き換える。
- git 連携が無効(`git.enabled` が false)のときは、フック用のコマンドは何もせずに終了コード0で終わる。

## 4. 設定ファイル `.bvc/config.json`

```json
{
  "format": 1,
  "track": ["*.bin", "mesh/**/*.dat"],
  "ignore": ["~*", "*.tmp"],
  "chunker": {"name": "fixed", "size": 4194304},
  "rules": [
    {"pattern": "result/*.bin", "chunker": {"name": "whole"}, "compression": "none"}
  ],
  "compression": "auto",
  "rename_threshold": 0.5,
  "threads": 0,
  "commit_verify": "exists",
  "git": {"enabled": false, "lock_file": "bvc.lock", "pre_commit": "snapshot"}
}
```

| キー | 意味 | 既定 |
|---|---|---|
| track | 追跡パターン(必須) | ― |
| ignore | 除外パターン | `[]` |
| chunker | 分割方式。`fixed`(size)、`gear`(min/avg/max/seed。avg は2の累乗)、`whole`(分割しない) | fixed 4MiB(仮) |
| rules | パターンごとに chunker と compression を上書きする規則。上から順に照合し、最初に一致したものを使う | `[]` |
| compression | `auto`(試し圧縮で判断)/ `none` / `zlib` | auto(仮) |
| rename_threshold | 名前変更とみなす類似度。0 より大きく 1 以下の数 | 0.5 |
| threads | 並列数。0 は CPU 数 | 0 |
| commit_verify | コミット時に、再利用する既存チャンクをどこまで検査するか。`exists`(存在とヘッダ)/ `full`(読み出してハッシュ照合) | exists |
| git.enabled | bvc.lock を自動更新する | false |
| git.pre_commit | 未コミットの変更がある状態で git commit したときの動き。`snapshot`(自動コミット)/ `reject`(拒否) | snapshot |

chunker と compression は、変更しても既存データの読み出しに影響しない。変更後は、境界が合わないため1回だけ重複排除が効かない。

### 4.1 分割方式の比較

| 方式 | 容量効率 | 破損時の影響範囲 | ツールなしでの復旧 | 速度 |
|---|---|---|---|---|
| fixed | 上書き型の変更に強い | そのチャンクを共有する全ての版 | 不可 | 速い |
| gear(CDC) | 挿入・削除にも強い | 同上 | 不可 | 遅い(純Python で約10MB/s) |
| whole | 変更のあった版ごとに全体を保存 | その内容を持つ版だけ | 圧縮なしなら可 | 速い |

分割しない場合でも、版の間でまったく変更の無いファイルは、1つの保存データを共有する。

### 4.2 最大安全の構成

```json
{"chunker": {"name": "whole"}, "compression": "none", "commit_verify": "full"}
```

- 保存データは元ファイルに1バイトのヘッダを付けただけのものになる。bvc が使えなくても、マニフェストの `sha256` の名前のファイルから先頭1バイトを除けば元に戻せる。
- コミットのたびに、再利用する保存データも読み出して照合する。
- 容量は、変更のあった版ごとにファイル全体が増える。
- ディスク故障には無力なので、別ディスクへの複製(要件定義書 T-7)と組み合わせることを推奨する。

## 5. git 連携

### 5.1 bvc.lock

作業フォルダ直下に置き、git で管理する。キーはソートし、末尾に改行を付ける(差分を安定させるため)。

```json
{
  "format": 1,
  "bvc_commit": 12,
  "files": {
    "model.bin": {"size": 1073741824, "sha256": "…", "manifest": "…"}
  }
}
```

- 正本は `files` の内容(manifest ハッシュ)。`bvc_commit` は参考情報。
- 現在位置が変わるたびに書き換える。未コミットの変更は反映されない。
- 内容(`files`)が移動先の版と同じ場合は書き換えない(sync で番号の違う同じ内容の版に移ったときに、git に差分を出さないため)。
- bvc が一度書いた後で `bvc.lock` が無くなった場合(bvc.lock の無いコミットへ git checkout した場合)は、作り直さない。作り直すと、git から見て追跡されていない bvc.lock が残り、bvc.lock のあるブランチへ戻る git checkout が拒否されるためである。bvc.lock のあるコミットへ戻れば、post-checkout の sync で合わせる。手で誤って消した場合は `git checkout -- bvc.lock` で戻す。

### 5.2 推奨する .gitignore

```
/.bvc/
*.bin        ← 追跡パターンと同じもの
```

### 5.3 フックの動作

| フック | 動作 |
|---|---|
| pre-commit | 未コミットの変更があれば、設定に従って自動コミット(`auto: git pre-commit`)して `git add bvc.lock` するか、拒否する。さらに、**ステージされた bvc.lock が、存在する健全な版と内容が一致しない場合は、git commit を拒否する**(非同期状態、手で編集した場合、gc 済みなど)。作業ツリーの bvc.lock がステージされていない場合は警告する。ステージに bvc.lock が無い(bvc.lock の無いコミットを作る)場合は、bvc.lock の検査と `git add` を省く |
| post-commit | git の HEAD と bvc の版の対応を pins に記録する(`bvc git pin`)。コミットに bvc.lock が無ければ何もしない |
| post-checkout | 作業ツリーの bvc.lock の内容が現在位置の版と異なれば `bvc sync` を実行する。失敗した場合は、目立つ警告を表示する(git checkout 自体は取り消せないため)。このときフックの終了コード(0 以外)が git checkout の終了コードになる(checkout 自体は完了している)。bvc.lock が無ければ何もしない(作業ファイルはそのまま) |

フックの中身(`<作業フォルダ>` は `/` 区切りの絶対パス):

```sh
#!/bin/sh
# bvc: bvc git install-hooks が設置したフック
exec python -m bvc -C "<作業フォルダ>" git pre-commit
```

- bvc.pyz から実行した場合は、`python -m bvc` の代わりに `python "<bvc.pyz のパス>"` を書く。
- 既存のフックに追記する行は、`exec` を付けない形(pre-commit は失敗を git に伝えるため `|| exit $?` を付ける)。

merge や rebase の後には自動実行しないので、必要に応じて `bvc sync` を手動で実行する。bvc.lock が衝突した場合はマージできないため、どちらか一方を選んで解決する。
